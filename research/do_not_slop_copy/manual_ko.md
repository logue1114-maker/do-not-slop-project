# Do Not Slop Project · UI 문장 교정 매뉴얼

조사·작성: 2026-10-04 UTC · 언어: 한국어 · 범위: 웹사이트/앱의 제목, 설명, 버튼, 오류, 확인, 빈 화면, 진행 상태

## 이 편의 목적

쓸모없는 문장을 덜어내되 필요한 뜻은 더 잘 보이게 한다. “짧게”, “친근하게”, “AI처럼 쓰지 말기”만으로는 실행 가능한 지시가 아니다. 화면마다 어떤 사실을 전달하는지, 실제 버튼이 무엇을 하는지, 지금 어떤 상태인지 확인한 뒤 삭제·교체·이동을 결정한다. 글자 수 감소와 귀여운 말투는 성공 기준이 아니다.

이 문서의 전후 예시는 모두 새로 만든 교육용 시나리오다. 특정 사이트의 한국어 번역·실측 화면·사용성 실험 결과가 아니다. 함께 제공한 HTML은 같은 데이터와 상태를 양쪽에 넣어 문구 차이를 확인한다. 가격, 파일 크기, 복원 기간 등의 숫자는 시나리오의 고정 조건이며 실제 서비스 제안이 아니다.

기존 조사에서 다룬 GOV.UK의 UI 작성, Refactoring UI의 시각 교정, Anthropic의 기본 미학 설명은 되풀이하지 않는다. 이번 편은 내용 설계자가 실제로 지적한 단어·문장·흐름과 한국어 교정 절차에 집중한다.

## 출처를 읽는 법

- 공식 지침: 해당 조직이 자사 시스템/콘텐츠에 적용하는 공개 가이드. 범용 법칙이나 한국어 표준은 아니다
- 저자 의견: 이름이 확인된 실무자의 해석·제안. 공식 가이드와 다르면 그 차이를 표시한다
- 저자 사례 보고: 작성자가 소개한 실제 또는 공개 설계 사례. 이 프로젝트가 그 사이트를 현재 감사했다는 뜻은 아니다
- 자체 제안: 아래 CP 규칙, 한국어 전후 문장, 절차, 시험의 통과 기준. 출처의 문장을 인용한 것이 아니다
- 실행 증거: 실제로 실행한 정적/브라우저 검사만 별도 검증 기록에 쓴다. 설계 의도를 사용성 향상 증거로 바꾸지 않는다

직접 인용은 출처당 25단어 이하로 제한한다. 이 패키지는 원문 링크만 제공하며 외부 기사 본문·그림·화면을 재배포하지 않는다.

## 실제 공개 비판을 교정으로 옮긴 6가지 사례

아래 ‘원문 사례’는 작성자가 보고한 당시 장면이다. 직접 현재 사이트를 조작해 얻은 감사 결과가 아니다. ‘한국어 교정안’은 이 프로젝트가 만든 제안이며 원저자의 개선본을 그대로 번역한 것이 아니다. 링크만 제공하고 원문 화면은 복사하지 않는다.

### 사례 A · 환영 문구를 전부 지우면 맥락도 사라진다

[Jakob Nielsen의 도입문 비판](https://www.nngroup.com/articles/blah-blah-text-keep-cut-or-kill/)은 기능 없는 환영을 제거하라고 하면서도 자신이 편집한 인터뷰 모음의 맥락은 남겼다.

- 원문에서 지적한 문제: 다양하고 뛰어난 사람이라는 소개가 인터뷰 링크보다 앞에서 길게 이어짐
- 자체 교정안: “참가자 인터뷰”라는 제목과 “이 인터뷰에서 참가자들의 경험을 읽을 수 있습니다” 같은 반복 안내를 함께 쓰기보다, 자료를 묶은 목적을 꼭 설명해야 할 때만 한 줄 남김
- 삭제/유지 경계: 칭찬과 분위기는 삭제 후보. 누구의 인터뷰인지, 어떤 행사의 자료인지 모르면 그 맥락은 유지
- 연결 규칙: CP01. 여기서 도출하는 것은 ‘도입 금지’가 아니라 ‘도입의 고유 정보 확인’

### 사례 B · 질문 이름을 다듬어도 중복 선택은 남는다

[Adam Silver의 배송/수령 사례](https://adamsilver.io/blog/if-youre-struggling-to-write-the-content-you-probably-have-an-interaction-problem/)는 수령 방식과 배송 유형의 질문 이름이 충돌하는 문제를 설명한다.

- 원문에서 제안·채택한 방향: 배송 세 종류와 매장 수령을 한 선택에 둠
- 자체 한국어 교정안: “주문을 어떻게 받을까요?” 아래 “일반 배송 / 다음 날 배송 / 저녁 배송 / 매장 수령”. 같은 질문을 다시 묻는 뒤 단계는 제거 검토
- 보존 조건: 실제 제공 여부, 비용, 지역, 시간 조건을 각 선택지에 연결. 모든 고객이 네 옵션을 사용할 수 있다고 새로 주장하지 않음
- 예외: 배송 주소를 알아야 가능 옵션이 계산되는 서비스는 그 선행 입력을 남김. 위 네 옵션을 무조건 합치라는 규칙이 아님
- 연결 규칙: CP03·CP04. 구조 수정 없이 긴 문구만 짧게 바꾸는 작업을 완료로 보지 않음

### 사례 C · 효익을 버튼 이름으로 쓰면 다음 화면을 속일 수 있다

[토스 작성자가 공개한 사례](https://toss.tech/article/21022)에서 “다른 곳에서 후불결제 하기” 버튼은 바로 결제를 열지 않고 사용 중인 브랜드를 알려주는 설문으로 이어졌다. 이 문구는 출처를 식별하기 위한 짧은 인용이다.

- 원문에서 지적한 문제: 미래의 제휴 효익과 즉시 열리는 화면이 다름
- 자체 한국어 교정안: “사용 중인 브랜드 알려주기”. 필요하면 주변 설명에서 제휴 검토에 사용하는 설문임을 확인된 사실에 맞게 알림
- 보존 조건: 설문 목적·수집 데이터·향후 제휴 확정 여부. 제안만 해도 결제 기능이 생긴다는 약속을 추가하지 않음
- 연결 규칙: CP04. CTA의 이름은 마케팅 팀의 기대보다 실제 다음 상태가 결정

### 사례 D · 검색 실패에 말장난을 넣어도 복구가 생기지 않는다

[NN/g의 오류 가이드](https://www.nngroup.com/articles/error-message-guidelines/)는 Disneyworld의 제한적인 조건으로 식당을 찾을 때 결과 없음이 말장난에 가려진 사례를 비판한다.

- 원문에서 지적한 문제: 검색 결과가 없다는 상황을 바로 알기 어려움
- 자체 한국어 교정안: “이 조건에 맞는 식당이 없습니다”. 현재 조건을 보존하고 실제 제공되는 “필터 변경” 또는 “필터 해제” 행동 연결
- 보존 조건: 검색 실패는 예약 실패·휴업·모든 식당 만석과 다름. 확인하지 못한 원인을 넣지 않음
- 예외: 다음 행동이 이미 명확하고 별도 버튼이 중복이라면 짧은 상태 설명만 유지할 수 있음
- 연결 규칙: CP05·CP07. 위트는 상황과 복구가 읽힌 뒤에도 필요할 때만 남김

### 사례 E · 친절한 말투여도 사용자를 입력 중에 혼내면 실패다

[Kate Kaplan의 조기 오류 비판](https://www.nngroup.com/articles/hostile-error-messages/)에는 LG의 우편번호 입력 시작, Sorel의 날짜 입력 완료 전 오류가 등장한다.

- 원문에서 지적한 문제: 아직 마치지 않은 입력을 오류처럼 취급함
- 자체 한국어 교정안: 입력 전에는 필요한 형식 예시, 완료/제출 후에는 확인된 제약. 오류를 공손하게 다시 쓰기만 하지 않고 발생 조건도 변경
- 보존 조건: 입력값, 필수 여부, 날짜 범위. 조기 경고를 지우면서 필요한 사전 제약까지 제거하지 않음
- 예외: 비밀번호 요구 사항처럼 즉각적인 진행 안내가 유용한 입력은 중립적인 조건 충족 표시를 검토. 모든 필드의 검증을 무조건 제출 후로 미루지 않음
- 연결 규칙: CP05. 문구 검수에 이벤트 시점이 포함되어야 함

### 사례 F · 거절하려고 거짓 자기소개를 클릭하게 하지 않는다

[NN/g의 거절 선택지 비판](https://www.nngroup.com/articles/shaming-users/)에서 Sears의 “No thanks, I don’t like deals.”는 제안을 닫기 위해 할인에 관심이 없다는 성향을 선언하게 했다. 이는 출처를 식별하기 위한 짧은 인용이다.

- 원문에서 지적한 문제: 제안 거절을 사용자 성향 비난으로 바꾸고, 실제 홍보 메일 수신 정보를 약하게 보여줌
- 자체 한국어 교정안: 수락 “할인 소식 이메일 받기”, 거절 “지금은 건너뛰기”. 실제 메일 목적·주기와 동의 조건은 함께 명시
- 보존 조건: 이메일 구독임을 공개하고 거절 시 가입하지 않음. 이메일 빈도는 확인된 정책에서 가져오고 새로 만들지 않음
- 예외: 실제로 작성물이 사라지는 이탈은 손실을 정확히 경고. 실제 결과 설명과 비난은 구분
- 연결 규칙: CP09. 중립적인 선택 문구와 실제 동의 동작을 함께 검사

## 작업을 시작하기 전: 문장을 지워도 되는지 판정하는 공통 절차

### 입력

1. 화면 ID와 목적: 유입/비교/편집/조회/결제/플레이 중 무엇을 하는가
2. 사용자 과제와 독자: 처음 쓰는가, 재방문인가, 전문 용어를 아는가
3. 상태: 미시작/입력/처리 중/성공/성공 0개/실패/권한 부족/취소
4. 문구 목록: 제목·라벨·도움·본문·버튼·툴팁·대화상자·접근성 이름과 각각의 위치
5. 실제 행동: 클릭 직후 상태, 목적지, 전송 대상, 공개 범위, 저장 범위
6. 확정 사실: 기능 명세·가격/결제 주기·자격·제약·복구·권한·상태의 근거
7. 용어집과 상황별 말투: 제품이 이미 쓰는 객체 이름, 평상시/실패/경고/축하의 톤

입력이 부족하면 문체 편집은 할 수 있어도 사실·결과를 만들어 채우지 않는다. 실제 행동, 요금, 자격, 복원 여부, 조회 상태가 미확인이면 해당 교정을 보류하고 필요한 확인을 명시한다.

### 보호 사실 장부

각 필수 사실에 ID를 붙인다. 예: F01=월 9,900원, F02=7일 뒤 자동 결제, F03=체험 종료 전 해지 시 요금 없음. 카피를 고치기 전 이 사실들이 어디 보이는지 적는다. 수정 후에는 같은 시점에 알아볼 수 있는 위치에 남았는지 확인한다. 단순 문자열 포함 여부로는 부족하다. “30일 뒤”와 “30일 안에”, “가능”과 “불가”, “무료”와 “체험 후 유료”는 같은 숫자가 있어도 다른 뜻이다.

보호 대상으로 먼저 잠근다: 가격·통화·세금/필수 비용·반복 결제, 약정과 취소/환불, 자격과 연령, 개인정보 수집/전송·권한, 위험·손실·복원 가능성, 현재 오류와 저장 여부, 실제 제한과 예외. “단”, “제외”, “불가”, “안 됩니다”는 삭제 금지어가 아니라 중요한 제한을 담을 수 있는 단서다.

### 판단과 편집 순서

1. 문장 역할을 하나씩 적는다: 이름/맥락/조건/결과/복구/절차/분위기. 하나가 여러 역할을 하면 나눌 후보로 본다
2. 이 문장만 알려주는 필수 사실이 있는지 먼저 확인한다. 있으면 유지·교체·이동하고 삭제하지 않는다
3. 제목·컨트롤이 이미 보여주는 사실의 재설명인지 검사한다. 중복이라면 먼저 삭제 후보로 둔다
4. “어떻게”를 길게 써야 하는 구조 자체가 잘못된 경우 재설계를 제안한다. 단어만 바꿔 모호함을 포장하지 않는다
5. 행동은 실제 핸들러에서, 상태는 데이터/이벤트에서, 주장은 명세/근거에서 다시 쓴다
6. 한국어 어순과 높임, 생략 주어, 부정 범위, 조사, 숫자 단위를 따로 검수한다
7. 삭제한 컨테이너 높이·중복 패널을 정리한다. 글만 빠진 빈 카드를 남기지 않는다
8. 기존 입력·권한·결제·전송·복구의 동작이 유지되는지 검사하고, 실제 검수한 범위를 기록한다

R0: 거짓 상태·행동, 필수 조건 은폐, 중요한 손실을 만들면 출고 차단. R1: 핵심 행동의 모호함·중복·잘못된 복구는 수정 후 재검수. R2: 뜻이 같은 말투 취향은 독자와 브랜드에 따라 선택한다. “앗”이나 “확인” 같은 단어의 존재만으로 R0를 판정하지 않는다.

- 기대 출력: 조건 불일치 설명과 필터 해제; 계정 데이터 없음 문구 금지

- 반례 기대 출력: 0개 성공 상태로 렌더링하지 않음; 권한/실패/로딩 분기 유지

### CP08 · 진행 문구는 실제 작업 상태와 함께 바뀐다

- 진행을 모를 때 무한 스피너도 작업명·실패 분기까지는 필요

- 적용 입력: 진행 이벤트 없음, 작업 running
- 기대 출력: 작업명+진행 중; 99%/10초/곧 완료 생성 없음
- 반례 입력: 서버에서 succeeded와 파일 URL 확인

2. 수신 목적·주기와 필요한 동의를 눈에 보이게 둔다

4. 거절/닫기 시 가입·전송·허용이 발생하지 않는지 시험한다

- 기존 구독 상태

**시험 레시피**

- 적용 입력: 수락은 이메일 구독, 거절은 현재 제안 닫기
- 기대 출력: 구독 명시, 거절 중립적; 거절이 유저 무관심 선언이 되지 않음
- 반례 입력: 이탈 시 작성 중인 응답 삭제, 재시작 불가
- 반례 기대 출력: 실제 손실 경고 유지; 중립적으로 숨기거나 위험을 제거하지 않음

## 한국어 적용은 영어 문장을 줄여 번역하는 일이 아니다

아래는 이 프로젝트의 독자 제안이다. [Mailchimp 번역 지침](https://styleguide.mailchimp.com/writing-for-translation/)은 문화별 격식과 명료함을 강조하지만, 한국어 문장을 직접 규정하지 않는다. [토스의 공개 원칙](https://toss.tech/article/21022)은 한국어 제품에서 확인할 가치가 있으나 토스 말투를 모든 제품에 복제하라는 허가는 아니다.

### 1. 자연스러운 대상 + 행동

- “당신의 성공을 잠금 해제하세요” → 지원 기능이 실제로 있으면 “보고서 만들기”. 성공을 보장하지 않는다면 성공이라는 약속도 제거
- “지금 당신의 워크스페이스를 발견하세요” → 실제 목적지에 따라 “작업 공간 열기” 또는 “작업 공간 둘러보기”
- “이것을 수행해 주세요” → 행위 대상이 둘 이상이면 “선택한 문서 이동”. 주변에서 대상이 명확하면 “이동”도 가능
- 영어 지침의 ‘첫 단어는 동사’를 직역해 “열기 작업 공간”으로 쓰지 않음

### 2. 해요체와 합니다체는 제품 맥락으로 고른다

대중 앱의 일상 안내는 “저장했어요”, 업무 도구의 상태는 “저장됨”, 공식 경고는 “저장하지 못했습니다”처럼 서로 다른 선택이 가능하다. 한 화면에서 임의로 섞지 않되, 경고의 의미를 약하게 만들면서 억지로 발랄하게 통일하지 않는다. 종결어미를 모든 문장에 자동 치환하는 방식은 쓰지 않는다. 단순 상태 라벨이 문장보다 자연스러운 곳도 있다.

### 3. 사용자의 감정과 능력을 대신 정의하지 않는다

“걱정 마세요, 아주 쉬워요”는 현재 실패를 해결하지 못한다. “처음이라 어렵죠?”도 경험을 추측한다. 쉬운지 평가하기보다 할 수 있는 행동을 적는다. “잘못 입력하셨네요” 대신 확인된 제약을 적는다. 감정적 도움은 실제 순간에 맞을 때 남긴다. 가입 절차 완료와 장기 목표 달성을 같은 크기의 축하로 처리하지 않는다.

### 4. 존대와 주어 생략을 기계적으로 하지 않는다

반복적인 “당신”, “귀하”, “고객님께서”는 종종 생략할 수 있으나, 나와 팀원·수신자·관리자가 섞인 화면에서는 주어가 필수다. “승인 후 알려드려요”는 누가 승인하고 누구에게 알리는지 모호할 수 있다. “관리자가 승인하면 신청자에게 이메일을 보냅니다”처럼 관계를 남긴다. 특정 직무의 정확한 전문 용어는 쉬운 단어라는 이유만으로 바꾸지 않는다.

### 5. 짧게 바꾸면서 부정과 예외를 없애지 않는다

- “만 19세 이상만 신청할 수 있습니다”는 “누구나 신청”으로 바꾸지 않음
- “결제하지 않으면 저장되지 않습니다”는 실제 의미가 “유료 결제 후 저장 가능”인지 확인하고 대상과 시점을 명확히 다시 쓰기
- “30일 이후 복원할 수 없습니다”는 “30일 복원”보다 긴 뜻이 있음. “30일 안에 복원할 수 있습니다. 이후에는 영구 삭제됩니다”처럼 중요한 경계 유지
- “동의하지 않음”은 부정 표현이라는 이유로 삭제하지 않음. 동의/거부 선택을 정확히 읽을 수 있어야 함

### 6. 용어는 데이터 객체와 맞춘다

“노트”, “메모”, “문서”를 재미를 위해 섞지 않는다. 제품에서 서로 다른 객체라면 오히려 구분해야 한다. 같은 객체인지 데이터·기존 화면을 먼저 확인하고 용어집으로 고정한다. 화면을 옮겼을 때 “임시 저장”이 “저장”이 되고 공개 발행이 “완료”가 되는 의미 변형도 검사한다.

## 스킬로 옮기기 위한 실행 계약

이 문서는 스킬 설치본이 아니다. 향후 구현이 읽을 입력·판정·출력·시험을 정의한다. rules.json의 규칙은 원문 인용이 아니라 교정 제안이며, source_ids로 근거를 추적한다.

### 최소 입력 예시

screen_id=export-dialog
surface_role=task
user_task=월간 보고서 내보내기
audience=업무 사용자
state=running
actual_actions=요청 중에는 내보내기 재실행 차단
known_product_facts=전체 8개, 현재 처리 3개, 종료 시간 미확인
protected_facts=내보내기 대상/현재 진행/완료 미확인
copy_inventory=제목·본문·버튼·접근성 이름·진행 표시와 위치
glossary=보고서/내보내기
tone_by_context=상태는 담담한 표현, 오류는 복구 중심

### 최소 출력

- rule_id와 실제 화면 위치
- 수정 전 문구 및 작업(유지/삭제/교체/이동/분리/합치기/재설계 필요/사실 확인 보류)
- 수정 후 문구. 삭제면 빈 문자열과 삭제 이유. 이동이면 새 위치
- 이유와 근거 유형: 출처 지침인가 저자 의견인가 자체 제안인가
- 보존한 사실 ID와 뜻을 확인한 방법
- 실제 버튼/상태/복구 동작 확인 결과
- 실행한 시험, 통과/실패/미실행, 남은 블로커

### 꼭 지켜야 할 보류 조건

핸들러를 못 봤는데 “발행”을 “저장”으로 바꾸지 않는다. 기간을 모르는데 “30일”을 채우지 않는다. API 실패를 성공 0개로 바꾸지 않는다. 저장 여부를 모르는데 “내용은 안전하게 보관됩니다”라고 쓰지 않는다. 취소/닫기/거절을 같은 동작으로 단정하지 않는다. 마케팅 성과와 제품 명세가 충돌하면 확인 요청으로 남긴다.

## 검수: 무엇을 실행하고 무엇을 아직 주장할 수 없는가

### A. 의미 보존 검사

같은 상태·입력·기능으로 수정 전후를 비교한다. 대상/수/시점/부정/조건/외부 영향/복구 범위를 사람이 읽어 확인한다. 숫자나 필수 단어의 자동 검사는 보조 수단이다. 단어 수·분량 감소율을 품질 점수로 쓰지 않는다.

### B. 행동 예측 검사

수정 후 버튼을 보기만 하고 예상 결과를 적는다. 실제 클릭 결과와 비교한다. 작성자·QA의 예상 확인은 전문가 점검이며 사용성 실험으로 부르지 않는다. 실제 사용자 연구를 한다면 대표 과제·참여자 맥락·문구와 레이아웃의 차이·혼란 지점·완료 여부를 사전 정의하고 보고한다. 이번 패키지는 그 실험을 수행하지 않았다.

### C. 상태 전이 검사

초기, 입력, 처리 중, 성공, 0개 결과, 오류, 권한 부족, 취소 상태를 강제로 만들 수 있게 한다. 처음에는 0개라며 CTA를 보여주고 로딩이 끝나면 목록을 뒤늦게 채우는 오류를 잡는다. 실패를 성공으로, 휴지통 이동을 영구 삭제로, 임시 저장을 발행으로 잘못 알리지 않는다.

### D. 입력 보존과 복구 검사

오류 뒤에도 유효 입력이 남는지 확인한다. “다시 시도”를 눌렀을 때 같은 확정적 제한 때문에 반복 실패하지 않는지 확인한다. 거절/취소는 요청을 보내지 않는지 확인한다. 필요한 위험 경고와 동의·승인 장치는 문장을 줄이는 과정에서 유지한다.

### E. 화면·접근성 검사

최소 지원 폭과 200% 확대에서 긴 한글 라벨이 잘리지 않는지 본다. 키보드로 모든 행동과 도움을 읽고 실행한다. 시각 라벨과 접근성 이름이 다른 행동을 말하지 않는지 확인한다. 선택 사항 설명을 숨겨도 이름·조건·오류 연결은 유지한다. 로딩 텍스트는 매 프레임·매초 반복 낭독하지 않는다. 실제 대상 제품의 지원 환경에서 추가 검증이 필요하다.

### F. 회귀 반례

가격·자격·연령·환불 불가·민감 데이터 전송·복원 불가를 담은 긴 안내, 낯선 조작의 접근 가능한 대안, 딥링크 맥락, 실제로 닫기만 하는 “확인”을 포함한 테스트를 반드시 넣는다. 이 반례를 삭제하는 스킬은 간결해 보여도 실패다.

## 패키지 파일

- manual_ko.md: 근거의 범위, 교정 규칙, 한국어 적용, 실행 절차
- sources.json: 확인한 원문과 출처 분류·한계·짧은 인용
- rules.json: 기계가 읽을 수 있는 입력/출력 계약과 9개 규칙·반례
- copy_examples.html: 외부 의존 없는 자체 제작 전후 비교. 실제 상품·계정·결제·메일 전송 없음
- validate.py: JSON 계약·문장/상태·민감 데이터 및 외부 의존 점검
- 새 검수 기록: 공개 준비 단계에서 실제 실행한 코드 검사와 미실행 브라우저·사용성 검수를 구분하여 작성

공개 시 제3자 원문·그림을 추가 복사하지 않는다. 이 파일에 포함된 이름은 공개 저자/조직의 출처 식별이며 사용자 정보나 사적 사례가 아니다. 출처의 현재 사이트 화면과 이 교육용 시나리오를 혼동하지 않는다.

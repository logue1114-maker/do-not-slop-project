# CP01 trial 01: public protocol and limits

## Fixed comparison

Question: for the single CP01 fixture, what observable differences appear between one ordinary-request implementation and one implementation given the same request plus bounded project instructions?

Before the runs, the English starter, fixture, common task brief, guided addition, verification checklist, review rubric, and one-repair allowance were fixed. The preparation was frozen on 2026-10-04 at 09:45:01 UTC. The [run record](run-record.json) anchors the retained bytes and original preparation hashes.

A and B were fresh runs without inherited conversation. Both requested and accepted the invocation model `gpt-6.1-sol` and reasoning effort `xhigh`. They received the same starter, fixture, checklist, prompt core, and no external dependency/service requirement. B additionally received the then-root [AGENTS.md, now archived byte-for-byte](../AGENTS.v1.md) and [CP01 guide](../../../guides/cp01-task-first.md). The ordinary-request arm did not receive those project instruction files, the original Korean image, the other arm's output, or a target final screen.

The [A brief](../prompts/A-plain.txt) is byte-identical to the core of the [B brief](../prompts/B-guided.txt); B appends the project-instruction read request. These are exact bounded public task briefs. Runtime operational handoff instructions are excluded, so these files are not claimed to be the complete runtime conversation. Shared system/tooling rules could not be removed.

## Work and repair

Each arm made one first-pass implementation. One bounded repair for verified functional, accessibility, rendering, or protected-content defects was permitted equally; subjective visual polishing and rerolls were excluded. No implementation repair was used. The [A](../alpha/index.html) and [B](../beta/index.html) runnable files are those exact first-pass bytes. A test-harness correction in B did not change its implementation.

The fixture protects the authored copy specimens, document records/order/modification values, same demo-only action, reset behavior, disclosure, and educational boundary. It allows layout, color, type, spacing, and supporting explanation changes.

## Capture and verification

Both default model outputs were captured using the same desktop frame (1165 × 747) and narrow frame (390 × 844); the reference was captured at the desktop frame. These JPG bytes are preserved. Browser scrollbar space can reduce inner content width by 15 pixels. These are browser-frame captures, not a native-phone test or proof that the nominal frame equals the content viewport.

[Observed browser checks](../checks/BROWSER_OBSERVATIONS.md) distinguish source checks, input spotchecks, and unrun accessibility gates. Screenshot-only inspection is not counted as a full interaction pass. No repairs were selected to favor an arm.

## Limits and stopping boundary

This is one descriptive pair, not a participant study or a deterministic replay. Exact backend revision, temperature/other sampling settings, service tier, seed, and full runtime parity are unavailable. No fixed time budget was enforced, and duration was not controlled. Equal task scope and repair allowance do not establish full runtime parity. The pair cannot isolate instruction effects from stochastic variation, run order, or reviewer expectations. It cannot establish general superiority, user preference, task-success improvement, or an effect size.

Both outputs still have green actions and neutral backgrounds. They do not establish that the design criticism is fully resolved. Native-phone, screen-reader, full keyboard-order/trap, zoom, and comprehensive accessibility review are unrun. Plugin installation/host activation and license selection are separate pending decisions.

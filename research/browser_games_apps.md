# 브라우저 게임·학습/생산성 앱 UI/UX 심층 매뉴얼

조사일: 2026-10-03 UTC · 범위: 2048 Classic, Lichess Chess Basics, Duolingo, Todoist

## 먼저 읽을 결론

이 네 제품은 같은 ‘앱 화면’으로 묶으면 안 된다. 2048은 판 전체를 읽는 짧은 반복 게임, Lichess 기본 학습은 조작법을 단계적으로 익히는 보드 튜토리얼, Duolingo는 긴 학습 경로와 한 문제 집중 화면을 오가는 학습 앱, Todoist는 입력·정리·실행·회수의 생산성 도구다. 따라서 핵심 선택은 색상보다 먼저 **사용자가 지금 무엇을 기억하고, 어디에 시선을 고정하며, 실패 뒤 무엇을 보존해야 하는가**다.

직접 관찰에서 특히 재사용 가치가 높은 점:

- 2048 점수 상자는 숫자 자릿수에 따라 너비가 달라졌다. 보드 너비는 유지됐고 HUD만 넓어졌다. ‘점수 카드 고정 너비’라는 관찰 규칙을 만들면 오류다
- Lichess는 이번 1180px 뷰포트에서 강좌 메뉴를 보드 아래로 보냈다. ‘데스크톱이면 항상 좌측 메뉴’라는 가정이 맞지 않았다
- Duolingo의 공식 화면은 탭별 채색 면적 차이가 크다. 학습 경로, 퀘스트, 정오답 상태를 하나의 60/30/10 비율로 통일할 근거가 없다
- Todoist에서 완료는 삭제와 다르며, 완료 기록을 보는 화면과 되돌리는 위치도 구별된다. 눈에 보이는 목록을 줄이면서 회수 경로를 보존하는 설계가 핵심이다

## 0. 근거 등급과 측정 규약

### 0.1 근거 구분

- **[O] 직접 관찰**: dot의 클라우드 Chrome에서 공개 페이지를 보고 클릭했다. 계정, 결제, 설치, 온라인 상대와의 대국, 외부 메시지 전송은 하지 않았다

## 1. 2048 Classic — 공간 상태를 읽는 단일 보드 퍼즐

첫 진입 보드 좌상단은 CSS (332.5,206.1875), 우하단은 (832.5,706.1875)였다. 판 면적은 CSS 뷰포트의 약 28.0%, 폭은 약 42.4%다. 이는 이 뷰포트에서의 점유율이고 권장 비율이 아니다. 설명 링크를 누르면 스크롤 위치가 변하므로 좌표값은 첫 진입에만 적용한다.

[O] 색은 배경 #faf8ef, 본문 #776e65, 판·점수 #bbada0, 재시작 #8f7a66, 값 2 타일 #eee4da, 값 4 타일 #ede0c9였다. 이후 큰 수는 더 채도가 높은 따뜻한 색을 얻지만 숫자를 계속 병기한다. 보드 밖 배경을 거의 비워 놓아 타일 밀도 증가가 진행 감각을 만든다.

### 1.3 실제 이동 경로

1. [O] 첫 진입: 점수 0, 최고 0, 숫자 2 두 개
2. [O] How to play: 모달 대신 페이지 아래 설명으로 스크롤. 설명 순서는 입력법→동일 숫자 합체→목표
3. [O] Start playing: 같은 페이지의 보드 쪽으로 복귀
4. [O] Left, Down 입력: 판 배치가 바뀌고 합체 점수 +4, SCORE 4·BEST 4 확인
5. [O] 순환 방향키로 계속 진행: 큰 타일, 빈 공간 감소, SCORE 492 관찰
6. [O] 이동 불가 상태: 최종 SCORE/BEST 1484, Game over 표시
7. [O] Try again: 점수 0·타일 두 개로 새 판. BEST 1484 유지
8. [O] 새로고침: 최고 점수 1484 유지. 현재 새 판도 두 타일로 표시

저장 방식의 내부 구현은 읽지 않았다. 새로고침 유지라는 관찰로부터 서버 계정 저장, 기기간 동기화, 무기한 영속성을 추정하지 않는다.

### 1.4 피드백, 실패, 회수

[O] 실패 오버레이는 보드 500×500 영역에만 붙고 rgba(238,228,218,0.73)다. 기존 타일은 투명하게 남는다. SCORE와 BEST, New Game은 오버레이 밖에 있다. 실패 원인인 가득 찬 판과 결과를 동시에 보며 재시작할 수 있다. 화면 전체를 가리거나 별도 결과 페이지로 보내지 않는다.

[O] 검사한 화면에는 Undo 버튼이 없었다. 이는 ‘전체 제품에 어떠한 되돌리기도 없다’는 소스 코드 검증 결과가 아니라, 이번 Classic UI의 노출 상태다. [U] 2048 달성 후 승리/Keep going 흐름은 실행하지 않았다.

[I] 이 장르는 작업 기억의 주요 대상이 현재 타일 위치·다음 합체 가능성이다. 점수와 최고 기록은 주변부에 있고, 메뉴 선택지를 최소화하여 조작법을 기억할 부담을 낮춘다. 반대로 도움말이 접힌 화면 아래에 있어 처음 입력법을 모르는 사람은 링크를 찾아야 한다. 이는 절대적인 정답이 아니라 진입 장벽과 즉시 플레이 사이의 선택이다.

### 1.5 모바일과 접근성 경계

[S] 공개 페이지 설명에는 손가락 스와이프 방식이 존재한다. [U] 모바일 실제 화면, 터치 충돌, 뷰포트 변화, 주소창 접힘, 가로 모드, 줌 200%, 스크린리더의 타일 좌표 읽기는 미검증이다. 이번 브라우저 API에 공식적인 뷰포트 재설정 기능이 없어 데스크톱 캡처를 휴대폰처럼 꾸며 증거로 삼지 않았다.

### 1.6 스킬화 가능한 규칙

- [P] IF 게임의 상태가 2차원 인접 관계에 달려 있다 THEN 판의 종횡비와 셀 간격을 우선 보존하고 보조 설명을 재배치한다
- [P] IF 점수 최대 자릿수를 모른다 THEN HUD 폭 증가 또는 예약 폭 정책을 명시하고 0/999/9999999 상태를 검수한다
- [P] IF 실패 직후 같은 규칙으로 재도전하는 것이 핵심이다 THEN 판 근처 결과·재시작을 제공하고 최고 기록과 현재 판 초기화를 분리한다
- [P] IF 전역 방향키를 사용한다 THEN 입력 필드·메뉴가 포커스를 가졌을 때 게임 입력이 작동할지 명시하고, 페이지 스크롤과의 충돌을 검사한다
- [P] 금지: 색만으로 숫자 구별, 새 게임에서 최고 기록까지 무설명 삭제, 동작 없는 Undo 가짜 버튼, 승리 화면을 보지 않았는데 관찰했다고 표기

### 1.7 예시 페이지 계약과 검수

## 2. Lichess Chess Basics — 제약된 행동으로 배우는 보드 튜토리얼

### 2.1 범위와 정보 구조

[O] [공개 체스 배우기](https://lichess.org/learn)는 계정 없이 강좌 지도를 보여 준다. 체스 기물→초급→중급→상급으로 묶고, 개별 카드에 이름과 짧은 행동 설명을 붙였다. 전체 진행도 0%와 시작 대상이 보인다. 온라인 대국에는 들어가지 않았다.

[O] 룩 카드 진입 후 ‘스테이지 1: 룩’ 소개와 시작하기가 나타났다. 시작하면 좌측 큰 판과 우측 설명 상자가 보인다. 이번 폭에서는 강좌 메뉴가 **판 아래**에 있었다. 최상단 서비스 메뉴는 남아 있으나 핵심 학습 진행은 판·오른쪽 설명·문제 번호 안에서 이루어진다.

[O] 배경은 낮은 채도의 밝은 중립색, 보드는 밝고 어두운 갈색 교대, 목표는 노란 별, 현재 학습 내용 헤더와 활성 문제는 파랑, 완료 문제는 녹색과 별이다. 유효 목적지는 기물 선택 후 녹색 점으로 나타났다. 경로 가이드는 보드 안 화살표여서 설명과 대상 위치가 분리되지 않는다.

[I] 큰 판이 단지 ‘시각 중심’인 것이 아니라 직접 조작 좌표계다. 우측 패널은 규칙 이름→짧은 정의→이번 행동→문제 진행 순서로 설명한다. 수많은 체스 규칙을 한번에 기억하게 하지 않고 현재 기물과 목표만 제시한다.

### 2.4 실패와 피드백의 설계 해석

[I] 불가능한 수는 파괴적 실패가 아니라 행동이 적용되지 않는 수준으로 처리했다. 초보에게는 ‘현재 합법 수를 보이는 것’이 복잡한 오류 설명보다 직접적인 안내가 될 수 있다. 다만 잘못된 수를 눌렀을 때 무슨 일이 일어났는지 모를 위험도 있어, 설명이 필요한 접근성 모드에서는 텍스트 피드백이 별도로 필요할 수 있다. 실제 스크린리더 테스트 없이 접근성 합격/불합격을 판정하지 않는다.

[I] 자동 다음 문제는 작은 성공의 리듬을 이어 준다. 반면 사용자가 방금 일어난 이동을 보고 싶을 수 있으므로 완료한 문제로 돌아가는 경로가 중요하다. 실제로 별로 바뀐 번호를 클릭해 재실행할 수 있었다.

- [P] IF 판+설명이 가용 폭에 들어오지 않는다 THEN 보드 크기와 설명 가독성을 기준으로 접는다. 기기명만으로 분기하지 않는다

- [P] 금지: 학습 도중 온라인 상대 찾기로 보내기, 완료 아이콘과 미완료 아이콘을 색만으로 구별, 튜토리얼 모든 문단 선공개, 맥락 없이 룰 전체 모달 반복

## 3. Duolingo — 경로형 학습과 문제 집중 화면의 분리

### 3.1 조사 범위와 버전 주의

[S] 실제 로그인 앱을 조작하지 않았다. 공식 블로그 2026-02-04 ‘core tabs’ 글의 iOS 화면, 2026-01-01 ‘Explain My Answer’ 정오답 화면, 경로 설계·연습 탭 설명을 사용했다. 출시 설명을 전체 사용자·모든 언어·플랫폼에 동일 적용된 라이브 상태라고 단정하지 않는다.

특히 2022 경로 글은 역사적 설계 취지에 유용하지만 현재 탭 위치·유료 여부를 그대로 가져오지 않는다. 최신 연습 탭 글은 무료 접근과 확장 메뉴 가능성을 설명한다. 따라서 ‘모든 Duolingo 화면은 하단 6탭’이라는 규칙도 부정확하다.

### 3.2 전체 구성과 화면 역할

[S/이미지 관찰] 공식 6화면 합성 이미지에는 경로, 퀘스트, 리그, 영상 통화, 프로필, 피드가 같은 하단 탐색 질서를 공유한다. 경로는 현재 시작 지점을 말풍선으로 강조하고 과거 완료·현재·미래 회색 노드를 구분한다. 퀘스트는 남은 기간과 누적 진행, 리그는 순위 행과 본인 행, 프로필은 사람과 누적 활동, 피드는 게시물과 반응이 주인공이다.

[S] 2026 설계 글은 헤더의 제목 위치는 일치시키되 목적에 따라 크기를 달리하고, 단순화가 정보 구분을 해치지 않도록 했다고 설명한다. 모든 섹션에 상자를 추가하지 않고 여백도 그룹 구분에 쓴다. [I] 반복 좌표는 길찾기를 안정시키고, 화면별 위계는 서로 다른 과업에 적응시키는 선택이다. ‘통일’이 모든 헤더 동일 높이를 뜻하지 않는다. [출처](https://blog.duolingo.com/core-tabs-redesign/)

### 3.3 첫 진입→핵심 행동→정오답→설명→복귀

- [S] 경로에서 현재 노드를 선택해 학습을 시작하는 구성. 역사적 경로 글은 학습·복습을 같은 순서에 넣고, 사용자가 다음 학습을 별도로 계획할 부담을 줄이는 취지를 설명한다. 완료 항목 재방문과 현재 위치로 돌아오기 기능도 설명한다. [2022 설계 설명](https://blog.duolingo.com/new-duolingo-home-screen-design/?region=central-and-eastern-europe)
- [S/이미지 관찰] 문제 화면은 상단 종료·진행·자원, 중앙 과제·캐릭터·질문·답안, 하단 결과와 다음 행동으로 나뉜다. 경로와 소셜 탐색은 문제 화면에 보이지 않는다
- [S/이미지 관찰] 오답 화면은 입력한 문장을 그대로 남기고 하단에 오답 상태·정답·선택 설명 버튼·Continue를 보여 준다. 오류가 난 단어에는 밑줄이 있어 색 외에도 차이가 나타난다
- [S/이미지 관찰] 설명 화면은 뒤로 가기, 선택된 언어 단위, 내가 쓴 답, 짧은 원리, 대조 예시, 설명 평가, Continue Lesson으로 구성된다. 설명을 닫고 수업으로 복귀하는 버튼이 존재한다
- [U] 해당 버튼을 실제 앱에서 누른 결과, 종료 확인, 중단한 문제 복원, 네트워크 실패, 수업 종료 보상은 직접 검증하지 않았다

공식 설명은 정답·오답 모두에서 추가 설명을 선택 가능하게 한다. 이 사례의 중요한 점은 ‘모든 실수에 긴 설명 강제 노출’이 아니라 즉시 정오답과 선택적인 깊은 설명의 분리다. [정오답 설명 공식 출처](https://blog.duolingo.com/explain-my-answer-now-free/)

### 3.4 크기와 색의 관찰 한계

| 항목 | 관찰·측정 단위 |
|---|---|
| 공식 6패널 이미지 | 실제 다운로드 1000×1337 이미지 px |
| 헤더 체계 합성 이미지 | 2778×2024 이미지 px |
| 오답/설명 원본 | 각각 379×816 이미지 px |
| 오답 결과 배경 | 이미지 y≈524부터 하단까지, 높이 약292px(화면 높이 약35.8%) |
| 오답 Continue | 이미지 x≈18–361, 높이 약48px |
| 의미 | 이미지에서 손으로 읽은 경계의 근삿값. CSS px·iOS pt·터치 영역 크기가 아님 |

기기 모델, OS 버전, 글자 배율, 앱 빌드, 원본 화면의 배율은 기사에 명시되지 않았다. 따라서 ‘버튼 높이 48pt’ 또는 ‘하단 피드백은 항상 화면 35.8%’로 쓰지 않는다. 글이 길거나 키보드가 열렸을 때는 다른 높이가 필요하다.

오답의 연분홍 넓은 면과 붉은 상태·버튼은 **오류 상태**를 표현하며, 경로의 초록은 현재 학습 행동·완료 맥락이다. 생산성 앱에서 같은 붉은색이 추가 행동을 나타내는 것과 의미가 다르다. 색상 이름만 묶어 범용 스킬로 만들지 않는다.

### 3.5 실패 자원과 기록 복귀

[S] 공식 Energy 설명은 기존 Hearts의 오답 비용과 다른 자원 모델을 소개하며, 일부 사용자 대상 시험·개선 중임을 명시한다. 현재 보이는 배터리를 ‘오답 1회마다 1 감소’로 추론하면 안 된다. [Energy 공식 설명](https://blog.duolingo.com/duolingo-energy/)

### 3.6 스킬 규칙·금지조건·검수

- [P] IF 긴 커리큘럼에서 다음 행동을 선택하기 어렵다 THEN 현재 학습 지점을 눈에 띄게 하고 ‘현재 위치로’ 복귀 수단을 둔다
- [P] IF 한 문제 풀이에 집중해야 한다 THEN 글로벌 탐색을 덜어내되 종료·진행·다음 행동은 유지한다
- [P] IF 오답 피드백을 준다 THEN 사용자 답과 정답을 대조 가능하게 보존하고, 상태·수정 대상·다음 행동 순으로 보여 준다
- [P] IF 설명이 길어질 수 있다 THEN 짧은 즉시 피드백과 선택 설명을 분리하고 돌아왔을 때 문항 상태를 유지한다
- [P] IF 자원이 학습 접근을 제한한다 THEN 비용·충전·보상 규칙을 화면에 맞는 사실로 명시한다. 하트·에너지 정책을 미리 가정하지 않는다
- [P] 금지: 실패 상태에 성공 녹색 재사용, 장식 때문에 정답·재시도 CTA 가리기, 색만으로 정오답 표현, 실제 앱 전체가 최신 기사 한 이미지와 같다고 단정

[P] 예시 페이지 상태: 학습 경로→문제 미입력→선택/입력→정답/오답→추가 설명→문제 복귀→수업 결과→경로. 실제 원작의 결제·광고·계정 시스템은 재현하지 않는다.

입력 요구: 학습 목표, 문항 유형, 정오답 판정 근거, 설명 분량, 중단 복원 정책, 진행률 분모, 자원 제한 유무, 모국어·학습 언어·긴 문자열 예시.

검수: 긴 질문, 두 줄·네 줄 답안, 잘못된 답 보존, 설명 뒤 복귀, 키보드가 켜진 화면, 스크롤 시 CTA 접근, 음성 사용 불가 대안, 색각 차이, 모션 감소, 현재 지점 복귀. 모바일 실제 앱 검수는 아직 별도 필요하다.

## 4. Todoist — 빠른 수집, 선택적 구조화, 완료 기록의 회수

### 4.1 범위

[S] 공식 기능 페이지의 데스크톱·iOS 이미지와 2026-09 갱신 도움말을 확인했다. 공개 기능 탭 선택 외에는 실제 계정 앱을 조작하지 않았다. 따라서 빈 계정 온보딩, 실제 저장 지연, 네트워크 실패, Undo 토스트 시간은 미검증이다. [공식 기능 화면](https://www.todoist.com/ko/features)

### 4.2 전체 구성·첫 행동

[S/이미지 관찰] 데스크톱 화면은 좌측 탐색과 우측 과업 목록이다. 좌측 상단 계정·알림·패널 접기, 이어 추가·검색·Inbox·Today·Upcoming·Filters, 그 아래 개인/팀 프로젝트가 모인다. 우측은 현재 보기 이름·표시 옵션·섹션·작업 행이다. 완료 원, 제목, 날짜, 프로젝트 태그가 같은 행 묶음 안에 있다. 목록 하단에도 추가 행동을 둔다.

[S] 공식 시작 설명과 작업 설명은 자연어로 제목과 날짜를 빠르게 수집하는 경로를 제시한다. 모든 분류값을 처음부터 필수로 채우게 하지 않는다. [시작 안내](https://www.todoist.com/help/todoist/get-started/get-started-with-todoist-OgNNJR), [작업 안내, 2026-09-30](https://www.todoist.com/help/todoist/features/introduction-to-tasks-080OAXric)

[I] ‘적기’와 ‘정리하기’를 분리하면 생각을 놓치기 전에 기록하고, 필요할 때 날짜·우선순위·설명을 더할 수 있다. 이것은 입력 시간을 줄일 수 있다는 설계 가설이며 이 조사에서 시간을 측정하지 않았다.

### 4.3 탐색 너비와 화면 밀도

공식 이미지 다운로드는 1120×566px이고 아래쪽이 잘려 있다. PNG로 무손실 형식 변환한 사본과 AVIF 원본을 모두 보관했다. 브라우저에 표시된 naturalWidth 1088 값과 다운로드 파일 1120이 달라, 최종 측정 기준은 파일 헤더의 1120×566으로 고정했다.

[S/이미지 관찰] 데스크톱 그림의 내부 앱 왼쪽 경계는 x≈34, 패널 경계는 x≈322, 오른쪽은 x≈1087이다. 따라서 **이 홍보 이미지 크롭에서** 좌측 영역은 약288 이미지 px, 보이는 내부 폭의 약27.4%다. 실제 기본 sidebar 너비, CSS px, 사용자 조절 가능 여부를 뜻하지 않는다. 메뉴 행 높이나 클릭 영역은 이미지에서 확정하지 않는다.

실제 숫자가 필요한 다음 검수에서는 앱의 로그인된 테스트 계정, 뷰포트, 사이드바 설정, 글자 배율을 고정한 뒤 DOM/접근성 사각형을 다시 측정해야 한다.

### 4.4 색·행동·기억 부담

[S/이미지 관찰] 작업 목록은 거의 흰색·회색이며 붉은색은 추가와 현재 선택에 쓰인다. 날짜는 초록, 일부 우선순위/프로젝트 표식은 색을 사용한다. 배경을 칠한 큰 카드 대신 얇은 구분선과 텍스트 정렬로 작업을 구분한다. 이미지의 저채도 픽셀 비중은 99% 안팎이지만 잘린 홍보 화면 수치다.

[I] 사용자의 주된 기억 부담은 목록의 장식이 아니라 ‘무엇을 언제 해야 하는가, 어디에 넣었는가’다. 고정 탐색과 검색, Today/Upcoming 투영은 같은 작업을 다른 질문으로 찾게 한다. 해당 작업의 프로젝트와 날짜를 행에서 볼 수 있어 열어 확인하는 횟수를 줄일 여지가 있다.

### 4.5 핵심 경로·실패·되돌리기·기록

[S] 문서상 경로:

1. Add task 또는 Quick Add로 수집
2. 제목·자연어 날짜 입력 후 확정
3. 작업을 열어 이름·설명·일정·우선순위 등 보완
4. 작업 옆 원을 눌러 완료, 활성 목록에서 제거되고 기록에 반영
5. 실수로 완료했다면 프로젝트의 Display→Completed tasks에서 다시 표시해 원을 눌러 미완료로 회수

[S] 반복 작업 완료의 Undo는 잠깐 나타나는 별도 경로이며, 지나간 반복 회차를 일반 작업처럼 모두 미완료로 돌릴 수 있는 구조가 아니다. 삭제 역시 완료와 다른 행동이다. 동일한 체크 애니메이션처럼 보이더라도 데이터 의미가 다르다. [작업 안내](https://www.todoist.com/help/todoist/features/introduction-to-tasks-080OAXric)

[S] 완료 기록은 프로젝트 안에서 보거나 Reporting에서 모아 볼 수 있으나, Reporting에서 편집/미완료 전환을 하지 않는다고 안내한다. 복원은 프로젝트로 돌아가 수행한다. [완료 기록 안내](https://www.todoist.com/help/todoist/features/view-completed-tasks-in-todoist-J19h2s)

[U] 실제 토스트가 몇 초 지속되는지, 어떤 완료 작업에 항상 등장하는지, 오프라인 큐/동기화 충돌을 어떻게 표시하는지는 검증하지 않았다. 문서의 ‘몇 초’를 5초 같은 수치로 바꾸지 않는다.

### 4.6 모바일 전환과 알림

[S] 공식 도움말은 모바일 탐색을 Browse 메뉴와 하단 내비게이션으로 설명한다. 데스크톱은 상단 왼쪽 패널 아이콘으로 사이드바를 숨길 수 있고, 숨긴 보기는 검색/명령 메뉴 등으로 접근 가능하다. 탭에 올린 보기는 Browse에서 제외되는 동작도 설명한다. [탐색 안내, 2026-09-16](https://www.todoist.com/help/todoist/features/customize-the-sidebar-and-navigation-menu-in-todoist-S9JLTYqZV)

[S/이미지 관찰] 공식 iOS 그림은 단일 목록 폭, 위쪽 현재 보기, 작업 행의 날짜·프로젝트 표식을 보여 준다. 이 이미지는 아래가 잘려 **하단 내비게이션과 추가 버튼 실제 위치를 눈으로 측정할 수 없다**. 해당 위치 설명은 도움말 근거다.

[S] 알림 배지와 작업 수는 설정 가능한 요소로 설명된다. 미완료 건수가 항상 동기부여라고 가정하지 않는 공식 설명도 있다. [배지 안내](https://www.todoist.com/help/todoist/features/show-or-hide-the-todoist-task-count-badge-T4A6Ey1he)

### 4.7 스킬 규칙·예시 페이지·검수

- [P] IF 생각을 빨리 수집하는 도구다 THEN 제목만으로 저장 가능한 기본 경로와 상세 편집 경로를 나눈다
- [P] IF 자연어 날짜를 파싱한다 THEN 해석된 날짜를 칩 등으로 명시하고 사용자가 수정/제거할 수 있게 한다
- [P] IF 완료 후 활성 목록에서 항목을 숨긴다 THEN 완료 상태 피드백과 나중의 회수 경로를 함께 설계한다
- [P] IF 반복 작업이다 THEN ‘이번 회차 완료’, ‘일정 변경’, ‘영구 종료’의 의미를 구별한다
- [P] IF 좁은 화면으로 옮긴다 THEN 핵심 보기·추가 행동·나머지 탐색의 분배를 새로 설계한다. 사이드바를 그대로 축소하지 않는다
- [P] IF 건수를 표시한다 THEN 그 숫자의 분모·조건·숨기기 정책을 정의한다
- [P] 금지: 완료=삭제 구현, 삭제 버튼을 되돌릴 수 있는 것처럼 표시, 실패한 저장을 성공 체크로 표현, 모든 필드 강제 입력, 데스크톱 hover만으로 중요한 행동 제공

[P] 예시 페이지는 Inbox/Today/Project, 빠른 추가, 날짜 해석 확인, 작업 상세, 완료, Undo, 완료 항목 보기, 회수까지 실제로 눌러볼 수 있게 한다. 샘플 작업만 로컬 저장하고 실제 외부 계정에 쓰지 않는다.

입력 요구: 작업 필수 필드, 날짜/마감일 구별, 시간대, 반복 규칙, 완료/삭제 보존 정책, 검색 범위, 동기화 여부, 개인정보 범위.

검수: ① 제목만 저장 ② 날짜 해석 수정 ③ 새 작업 위치 확인 ④ 완료 후 목록·카운트 변화 ⑤ 즉시 Undo ⑥ 나중에 Completed 표시 후 회수 ⑦ 반복 작업 다음 회차 ⑧ 긴 제목 두 줄 ⑨ 저장 실패 후 입력 보존 ⑩ 모바일 키보드·하단 CTA ⑪ 숨긴 보기 검색 ⑫ 필터 때문에 안 보이는 작업과 삭제된 작업 구별.

## 5. 사례를 구현 스킬로 변환하는 공통 계약

### 5.1 최소 입력을 먼저 확정한다

새 UI를 만들 때 장르 이름만 받지 말고 다음을 구조화한다.

1. 사용자의 한 세션 목적과 주된 행동
2. 핵심 상태의 공간 관계: 2D 판/순서 있는 경로/독립 작업 목록
3. 필수 화면: 진입, 행동 전, 행동 중, 성공, 실패, 취소, 기록, 복귀
4. 입력 장치·최소 뷰포트·언어·글자 확대
5. 무엇을 보존할지: 현재 입력, 최고 기록, 문제별 완료, 작업 기록
6. 오류 비용: 무효 클릭/진행 손실/데이터 삭제/외부 전송
7. 숫자 최대 길이·본문 최대 길이·목록 크기
8. 출처 등급: 실측, 공식 이미지, 설명, 제안의 구분

### 5.2 레이아웃 선택 if/then

- IF 모든 판단이 공간 인접성에 의존한다 THEN 보드 중심형을 우선한다
- IF 하나의 규칙을 처음 익힌다 THEN 과제 하나와 바로 옆 설명으로 좁힌다
- IF 다음 학습 순서 선택이 불필요한 부담이다 THEN 추천 경로와 현재 지점 복귀를 둔다
- IF 여러 프로젝트를 반복 왕복한다 THEN 고정 탐색과 검색을 우선하고 좁은 폭에서는 우선순위를 재배분한다
- IF 실패가 재도전의 일부다 THEN 실패 원인이 된 맥락과 재시작을 가까이 둔다
- IF 실행 취소가 데이터 의미를 바꾼다 THEN 취소 가능한 범위·기간·회수 위치를 먼저 설계한다
- IF 원본 화면의 CSS 수치가 없다 THEN 이미지 px를 앱 토큰으로 승격하지 않는다. 새 토큰은 제안값임을 명시한다
- IF 정체성이 아니라 상태를 알리는 색이다 THEN 같은 상태에는 일관되게 쓰고 색 외의 표시를 병행한다

### 5.3 절대 하지 않을 일반화

- ‘유명 앱이니 그 버튼/색/폭이 최적’이라고 결론내리지 않는다
- 웹·iOS·Android·실험군·유료/무료 버전을 한 제품 화면으로 섞지 않는다
- 잘린 홍보 이미지로 화면 하단 동선을 확정하지 않는다
- 실제로 누르지 않은 실패·취소·복귀 단계를 직접 관찰이라고 쓰지 않는다
- 픽셀 하나의 거짓 정밀도보다 범위·조건·측정법을 우선한다
- 모든 화면을 카드로 만들거나 모든 색을 중립화하는 단일 미학을 강요하지 않는다

### 5.4 예시 페이지에 반드시 보여 줄 검수 장치

[P] 각 예시는 제품 복제본 대신 원리를 분리해 검수하는 작은 샌드박스다. 화면 상단에 원리·현재 상태·초기화 범위, 옆에 근거 링크를 둔다. ‘성공/실패 보기’ 같은 검수용 상태 전환은 별도 표시하며 실제 사용 동선과 섞지 않는다. 한 버튼을 눌렀을 때 상태·화면·기록 중 무엇이 변했는지 확인 가능해야 한다.

검수 순서는 사용자가 원한 순서를 유지한다: **사례별 매뉴얼 검수→if/then 규칙 검수→작동 예시 검수→수정 후 스킬화**. 이 문서는 연구 및 규칙 초안이며, 앱 두 사례의 라이브 조작과 모바일 실측이 남아 있다. 검수 전부터 모든 규칙을 확정된 공통 스킬로 저장하지 않는다.

## 6. 증거 색인과 남은 일

원본 제품 캡처와 재생 자료는 포함하지 않는다. 이 문서의 관찰·수치에는 원래의 범위와 한계가 적용된다.

- 2048: 첫 진입·도움말·진행·종료·재시작·새로고침 스크린샷, 측정 JSON
- Lichess: 지도·소개·연습·합법/불법 입력·단계 완료·지도 복귀·재진입·재실행, 측정 JSON
- Duolingo: 공식 모바일 원본 4개, 이미지 출처 manifest 2개
- Todoist: 공식 데스크톱/iOS 원본과 PNG 사본, 이미지 출처 manifest
- 공통: 채도 면적 측정 코드와 JSON. ROI와 데이터 손실/한계를 코드 및 본문에 기록

추가 검증이 필요한 것:

1. 모바일 2048/Lichess 실제 화면과 터치·키보드 충돌
2. Duolingo/Todoist 별도 테스트 계정에서 직접 진입→실패→회수 전 과정
3. 긴 문자열·글자 확대·저시력/스크린리더·모션 감소
4. 게임 승리/전체 강좌 완료와 그 이후 기록
5. 예시 페이지 제작 후 사용자가 목적을 설명받지 않고 첫 행동을 찾는지 검수

새 테스트 계정 생성·로그인·알림 권한·데이터 전송은 이 조사에서 실행하지 않았다. 후속 실측은 필요한 권한과 샌드박스 범위를 정한 뒤 진행한다.

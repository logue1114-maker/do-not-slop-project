# 용도별 UI UX 심층 매뉴얼 시리즈 설계

작성일 2026년 10월 3일
상태 사용자 검수 전 초안
목적 게임 개발과 여러 학습 앱 제작에서 실제 사용 맥락에 맞는 화면과 동선을 설계하고 검증하기

이 문서는 유명 서비스의 겉모양을 모아 복제하는 자료집이 아니라, 실제 제품을 관찰한 증거를 구현 가능한 규칙으로 바꾸는 매뉴얼의 설계도다. 현재 문서에는 조사할 범위, 기록 양식, 공식 기준과 검수 방식이 들어 있다. 개별 유명 제품의 전 화면을 직접 실측했다는 의미는 아니다. 아직 관찰하지 못한 값과 기능은 미확인으로 남긴다.

핵심 결과물은 용도별 본편, 플랫폼별 보충편, 재사용 가능한 증거 기록으로 나눈다. 각각의 본편은 관찰 가능한 범위에서 2~4개 사례를 깊게 조사한 뒤, 대조 분석 → 원리 → 적용과 비적용 조건 → 구현 토큰과 상태 → 검수 시나리오 순서로 완성한다. 사례 수는 이번 시리즈의 편집 기준이며 UX의 보편 법칙이 아니다.

## 1 분류 원칙

### 목적과 플랫폼을 서로 다른 축으로 기록한다

웹게임은 실행 플랫폼을, RPG와 카드게임은 게임의 성격을 가리킨다. 따라서 세 항목을 같은 수준의 상호 배타적인 장르로 취급하지 않는다. 브라우저에서 실행되는 RPG는 RPG 본편과 웹게임 보충편을 함께 사용한다. 네이티브 모바일 카드게임은 카드게임 본편과 모바일 입력 보충편을 조합한다.

분류 축은 다음과 같다.

| 축 | 기록할 내용 | 예시 |
| --- | --- | --- |
| 사용자 목적 | 무엇을 이루려고 하는가 | 캐릭터 성장, 상품 선택, 정보 확인, 강의 수강, 반복 학습 |
| 상호작용 유형 | 어떤 판단과 입력을 반복하는가 | 실시간 조작, 턴제 선택, 비교, 검색, 읽기, 문제 풀이 |
| 실행 플랫폼 | 어디서 실행되는가 | 웹, PC 네이티브, iOS, Android, 콘솔 |
| 입력 환경 | 어떻게 조작하는가 | 마우스, 키보드, 터치, 컨트롤러, 보조 입력 |
| 시간과 위험 | 시간이 얼마나 촉박하며 실수 비용은 무엇인가 | 전투 중, 숙고 가능한 선택, 유료 결제, 저장되지 않은 작성 |
| 사용 상태 | 처음인가, 반복 이용인가 | 최초 방문, 튜토리얼, 복귀, 숙련, 로그아웃, 오프라인 |
| 정보 형태 | 어떤 내용을 구분해야 하는가 | 공간, 계층, 표, 카드 목록, 긴 본문, 미디어, 진행 상태 |

사용자에게 보이는 목차는 게임·웹·앱으로 쉽게 찾도록 제공하되, 내부 사례는 위 축으로 교차 검색한다. 같은 학습 제품의 웹판과 앱판은 서로 다른 관찰 세션으로 저장하고, 같은 원리를 중복 작성하지 않는다.

| A02 | 읽기와 미디어 소비 앱 | 콘텐츠 탐색, 플레이어, 재생 큐, 오프라인, 이어보기, 기기 전환 | 발견 → 읽기나 재생 → 제어 → 저장 → 중단 → 재개 |

A01은 웹에서도 사용할 수 있다. W03은 모바일 앱에서도 사용할 수 있다. W와 A는 찾아보기용 책장일 뿐 기술적 적용 범위를 제한하지 않는다. 학습 제품은 수강형과 문제 풀이형의 목표·피드백 구조가 달라 별도 본편으로 유지한다. 학습 앱의 체류 시간이나 연속 이용 기록만으로 학습 성과를 증명했다고 쓰지 않는다.

### 우선 작성 순서

먼저 G01·G02·P01·A01·W03을 진행해 게임 개발과 학습 앱 제작에 바로 활용한다. W01·W02를 이어서 작성해 비교·검색·정보구분 원리를 보강한다. 나머지 본편은 실제 제작 계획에 맞추어 확장한다. 한 번에 모든 장르를 얕게 채우기보다 각 편의 핵심 동선과 2~4개 사례를 완결한다. 이 순서는 제안이며 사용자가 지정하는 제작 순서가 우선한다.

## 2 각 본편의 고정 목차

1. 이 매뉴얼의 사용자와 해결하려는 작업
2. 적용 범위와 제외 범위
3. 사례 선정 이유와 관찰 가능 범위
4. 서비스별 전체 화면 지도와 주요 메뉴 구조
5. 핵심 동선의 시작부터 완료와 복귀까지
6. 화면별 레이아웃과 정보 우선순위
7. 컴포넌트 실측과 상호작용 상태
8. 색상·텍스트·이미지·여백·밀도의 역할
9. 초보·숙련 및 플랫폼 간 차이
10. 같은 작업을 기준으로 한 사례 대조
11. 재사용할 원리와 사용하지 말아야 할 조건
12. 구현 토큰·레이아웃 제약·동선·상태 계약
13. 접근성·성능·현지화 검수
14. 실패 사례와 수정 전후 검증
15. 근거 목록·미확인 항목·변경 이력

‘전체 화면’은 제품의 모든 비공개 기능을 조사했다는 뜻이 아니다. 먼저 조사 범위를 선언한다. 예를 들어 ‘비로그인 상태의 검색부터 상품 상세 및 장바구니 진입 전까지’ 또는 ‘공식 가이드에 공개된 인벤토리와 장비 비교 화면’처럼 경계를 적고, 그 범위 안에서 화면과 상태를 빠짐없이 지도화한다.

각 본편에는 다음 산출물이 함께 있어야 한다.

- 화면 지도와 과제별 동선
- 같은 축으로 비교한 사례표
- 원본 증거와 연결된 화면 주석도
- 컴포넌트 측정표와 상태표
- 원리별 근거와 적용 조건
- 구현용 규칙과 아직 결정하지 않은 값
- 재현 가능한 검수 시나리오

## 3 사례 선정과 조사 범위

### 사례 2~4개를 고르는 방법

같은 목적을 다른 방식으로 해결하는 사례를 고른다. 가장 유명한 네 제품을 자동 선택하지 않는다. 기본 사례 하나, 다른 정보 구조나 입력 방식의 대조 사례 하나를 포함하고, 필요하면 높은 정보 밀도의 숙련자 사례와 모바일 사례를 더한다. 가능하면 규모·언어·사용자 구성의 편향도 기록한다.

비교 가능성을 먼저 확인한다.

- 같은 사용자 과제를 비교하는가
- 같은 핵심 상태를 볼 수 있는가
- 무료 화면과 유료 화면을 뒤섞어 결론 내리지 않았는가
- 관찰 시기의 버전과 플랫폼 차이가 설명되어 있는가
- 초기 계정과 숙련 계정의 콘텐츠 양 차이가 기록되어 있는가
- 결제·로그인·진행 잠금 등 관찰 경계가 표시되어 있는가

유명 제품에 있다는 사실만으로 좋은 UX라고 판단하지 않는다. 매출·이용자 수·시장 지위는 인터페이스 설계가 좋다는 인과 증거가 아니다. 성공한 제품 안에도 특정 사용자에게 불편한 부분, 사업상의 최적화, 역사적으로 남은 패턴이 있을 수 있다.

### 관찰 경계

직접 사용 가능한 공개 화면은 직접 관찰한다. 설치·결제·새 계정·개인 정보 입력이 필요한 조사라면 허용 범위와 권한을 확인한다. 직접 접근할 수 없으면 제작사 공식 매뉴얼, 공식 게임플레이 영상, 공식 도움말의 범위만 분석한다. 영상의 화면 크기나 움직임은 영상에 나온 상태의 증거이지 현재 제품 전체의 증거가 아니다.

관찰 가능한 사례가 두 개 미만이면 ‘조사 초안’으로 공개한다. 2~4개가 있어도 핵심 상태가 공식 설명뿐이면 ‘문헌 중심 비교’로 적는다. 미관찰 영역을 그럴듯한 화면이나 수치로 채워서 심층 실측판이라고 부르지 않는다.

## 4 근거를 나누는 공통 표기

모든 중요한 주장과 숫자에 아래 유형을 붙인다. 주장의 종류와 출처의 종류는 다른 필드다.

| 유형 | 의미 | 허용하는 표현 | 금지하는 확대 해석 |
| --- | --- | --- | --- |
| OBS | 직접 관찰한 사실 | 이 세션에서 메뉴를 닫자 이전 항목으로 포커스가 돌아옴 | 모든 기기나 모든 버전에서 동일하다고 단정 |
| MEASURED | 정의된 방법으로 잰 값 | 캡처 이미지에서 보이는 사각형의 너비를 측정함 | 보이는 사각형을 실제 클릭 영역이라고 단정 |
| OFFICIAL | 제작사 설명이나 공식 기준 | 공식 문서가 특정 동작이나 기준을 안내함 | 해당 제품이 기준을 실제 충족한다고 단정 |
| INFERRED | 관찰에서 도출한 해석 | 선택한 항목과 상세가 가까워 왕복 탐색이 줄 가능성이 있음 | 관찰만으로 사용성이 입증되었다고 단정 |
| RECOMMENDED | 우리 프로젝트에 제안한 설계 | 터치 버전은 선택 후 확정 단계를 둠 | 유명 제품의 실제 구현이라고 표기 |
| UNKNOWN | 관찰하지 못했거나 불명확한 값 | 실제 hit area, 네트워크 실패 처리 미확인 | 빈칸을 관행적인 값으로 채움 |

출처 유형에는 live_product, official_document, official_video, official_screenshot, user_test, project_prototype 등을 사용한다. 공개 자료 한 장에서 직접 보이는 배치에 대한 OBS와 제품을 직접 조작한 OBS는 source_type과 observation_mode로 구분한다.

신뢰도는 높음·중간·낮음으로 기록하되 근거를 적는다. 공식 문서라는 이유만으로 현재 UI 실측 신뢰도가 높아지는 것은 아니다. 정밀 DOM 측정은 해당 세션의 기하 측정에는 강하지만 사용자 효과를 증명하지 않는다. 동일 화면을 다시 측정할 수 없는 캡처는 반올림과 오차 범위를 명시한다.

## 7 실측 사전

### 단위와 좌표

| 지표 | 정의 | 주의점 |
| --- | --- | --- |
| 보이는 너비와 높이 | 지정 좌표계에서 시각 경계의 width와 height | 그림자 포함 여부, 둥근 모서리와 투명 영역의 기준을 명시 |
| 실제 조작 영역 | 해당 입력을 받는 영역 | 이미지로만 확인할 수 없으며 겹침 영역을 점검 |
| 가로 점유율 | 요소 너비 ÷ 기준 영역 너비 | viewport 기준과 부모 패널 기준을 섞지 않음 |
| 세로 점유율 | 요소 높이 ÷ 기준 영역 높이 | 긴 페이지 전체 높이와 현재 viewport 높이를 구분 |
| 면적 점유율 | 영역의 측정 면적 ÷ 기준 영역 면적 | 겹치는 사각형을 더하지 않고 필요한 경우 합집합 사용 |
| 정규화 위치 | 기준 영역 원점으로부터 x/W와 y/H | 왼쪽 위 또는 중심 좌표인지 명시 |
| 간격 | 인접한 시각 경계나 hit 영역 사이 거리 | 같은 기준끼리 측정하고 두 기준을 혼합하지 않음 |
| 화면 밀도 | 정의한 정보 항목이나 조작 요소 수와 점유율 | 요소 수가 많다는 사실만으로 인지 부하를 확정하지 않음 |
| 동시 선택지 | 같은 판단 단계에서 선택 가능한 항목 | 숨어 있는 항목, disabled 항목, 중첩 단계와 구분 |
| 탐색 깊이 | 시작점에서 목표까지 필요한 메뉴나 화면 전환 | 탭·스크롤·단축키·입력·의사결정을 별도 집계 |

스크린샷의 측정값은 해당 이미지의 픽셀이다. CSS px는 웹 레이아웃 단위이고 실제 하드웨어 픽셀과 다르다. Android dp와 Apple pt는 각 플랫폼의 논리 단위이며, CSS의 인쇄 단위 pt와 Apple UI point를 같다고 취급하지 않는다. W3C의 CSS pixel 설명은 [Target Size Minimum의 용어 정의](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html#dfn-css-pixels)를 따른다.

비율은 기록을 위한 값이지 목표 비율이 아니다. ‘주 콘텐츠는 무조건 화면의 70%’ 또는 ‘주색·보조색·강조색 60:30:10’ 같은 숫자를 보편 정답으로 만들지 않는다. 실제 관찰된 여러 상태의 범위, 왜 그 배치가 필요한지, 프로젝트의 콘텐츠와 입력 조건이 맞는지를 설명한다.

### 색상 비율

색상을 분석할 때는 두 종류의 결과를 분리한다.

1. 픽셀 분포: 이미지 안에 특정 색이나 색 군집이 차지한 비중
2. 의미 역할: 배경, 표면, 본문, 보조 텍스트, 상호작용, 선택, 경고, 성공이 쓰인 위치와 역할

사진·게임 장면·썸네일·동영상은 UI 색상과 따로 분석한다. 전체 화면을 포함한 분포와 UI만 추출한 분포를 함께 낼 수 있지만 어떤 마스크를 적용했는지 남긴다. 그라데이션, 반투명 패널, 안티앨리어싱, 캡처 색공간, HDR 변환, 테마와 동적 배경 때문에 값이 달라질 수 있다. 픽셀 수가 많다는 사실을 시각적 중요도가 높다는 뜻으로 해석하지 않는다.

색상 마스크의 포함과 제외 규칙을 정하고, 경계가 모호하면 수치에 오차 또는 대략값 표기를 붙인다. 군집화의 군집 수와 색 공간이 달라진 결과를 같은 지표처럼 비교하지 않는다. 의미 역할 판독과 실제 사용자 시선은 다르며, 시선 추적 없이 ‘시선이 먼저 간다’는 실증 주장으로 쓰지 않는다.

### 동선과 시간

시간은 입력 시점 → 즉각 피드백 → 주요 결과 표시 → 작업 완료를 나눠 기록한다. 동영상 프레임으로 잰 값은 영상의 frame rate와 편집 여부에 제한받는다. 반복 측정 없이 한 번 잰 값을 제품의 평균이나 최악값으로 부르지 않는다.

동선은 클릭 수만 계산하지 않는다. 화면 전환 수, 스크롤 거리, 입력량, 선택지 수, 새로운 개념 수, 확인·취소·복귀 비용, 중단 후 재개 비용을 함께 적는다. 적은 클릭이 항상 좋은 것은 아니며 비가역 행동의 확인 단계는 오류를 줄이기 위한 비용일 수 있다.

- 앱 중단과 재개
- 콘텐츠가 많거나 번역이 길어진 상태

온라인 게임에서 확정된 행동, 다른 사람에게 이미 전송된 행동, 유료 주문처럼 되돌릴 수 없는 동작은 ‘언제나 undo 제공’이라는 일반 규칙을 붙이지 않는다. 확정 전 예측·확인, 확정 후 결과 설명, 가능한 회복 경로를 각각 기록한다.

## 9 대조 분석에서 원리로 넘어가는 방법

### 비교표에 필요한 열

같은 사용자 목표, 입력 방법, 콘텐츠 양, 시간 압박, 결정 비용, 화면 구조, 조작 영역, 정보의 동시 표시, 피드백, 오류 회복, 측정 조건, 관찰 한계를 나란히 놓는다. 브랜드 전체에 총점을 매기기보다 과제별 강점과 비용을 분석한다.

### 원리 카드

```json
{
  "principle_id": "",
  "problem": "",
  "principle": "",
  "evidence_ids": [],
  "evidence_strength": "observational|official-guidance|user-tested|mixed",
  "reasoning_summary": "관찰에서 도출한 공개 가능한 짧은 해석",
  "use_when": [],
  "avoid_when": [],
  "tradeoffs": [],
  "accessibility_considerations": [],
  "counterexample_or_boundary_case": null,
  "implementation_contract_ids": [],
  "test_ids": [],
  "unresolved_questions": []
}
```

최소 하나의 적용 조건과 비적용 조건을 쓴다. 예를 들어 ‘목록과 상세를 나란히 보여준다’는 원리는 반복 비교가 잦고 가로 공간이 충분할 때 적합할 수 있다. 좁은 창, 한 가지 판단에 집중해야 하는 과제, 상세 정보가 아주 길 때는 접기나 화면 분리가 필요할 수 있다. 이는 연구 가설과 설계 제안이며 사용자 시험 없이는 효과를 입증했다고 쓰지 않는다.

관찰된 패턴의 공통점만 추출하지 않는다. 왜 어떤 사례는 다른 방식을 쓰는지, 해당 선택이 다른 사용자에게 언제 비용이 되는지를 함께 설명한다. 재사용하는 것은 로고·일러스트·고유 화면 복제품이 아니라 목적, 정보 관계, 상호작용의 구조다.

## 10 구현 규칙과 토큰 스키마

디자인 토큰은 최종 값의 목록만이 아니라 값의 근거와 적용 범위를 포함한다. 아래 null은 프로젝트별 결정이 필요함을 뜻한다.

```json
{
  "token_id": "control.primary.min_hit_size",
  "semantic_role": "primary-action-hit-target",
  "value": null,
  "unit": "css_px|dp|apple_pt|engine_unit",
  "platform": "",
  "input_method": "",
  "density_mode": "comfortable|compact|other",
  "state_scope": [],
  "origin": "official-baseline|case-measurement|project-decision",
  "source_or_decision_id": "",
  "responsive_behavior": null,
  "accessibility_constraints": [],
  "validation_method": "",
  "status": "proposed|tested|accepted|rejected"
}
```

값을 정하는 순서는 해당 플랫폼의 기준 → 핵심 과제와 데이터 양 → 실제 사례의 범위 → 프로토타입 → 검수다. 공식 최소 기준을 충족한다고 최적 크기가 확정되는 것은 아니다. 같은 버튼의 시각 크기와 hit area가 다른 경우에도 서로 겹치거나 혼동되지 않아야 한다.

필수 토큰 범주와 계약은 다음과 같다.

- 색상: canvas, surface, text, secondary-text, action, selected, danger, warning, success. 의미 역할과 테마별 대비를 함께 지정
- 타이포그래피: 제목·본문·보조·숫자·버튼 레이블·자막의 역할, 크기 단위, 확대, 줄바꿈과 잘림 정책
- 공간: 외부 여백, 관련 정보 사이 간격, 그룹 사이 간격, hit 간격. 임의의 모든 값에 같은 배수를 강제하지 않음
- 레이아웃: 최대 콘텐츠 너비, 패널 최소 너비, 우선적으로 접을 영역, 고정 영역과 스크롤 영역, 안전 영역
- 입력: focus, press, hover, select, disabled, unavailable reason, keyboard/controller 경로
- 동작: pending, immediate feedback, complete, fail, cancel, retry, duplicate protection
- 움직임: 목적, 시작과 종료 조건, 동작 감소 대안, 필수 정보가 움직임에만 있지 않도록 할 대안
- 데이터: 목록·문장·숫자·이미지·오류 메시지의 짧음·김·없음·과다·부분 로딩 경계

최종 구현 문서는 토큰만 던져 주지 않는다. 사용 컴포넌트, 주요 상태, 데이터 모델의 의미, 레이아웃 전환 조건, 포커스 규칙, 오류 회복, 통과해야 할 시험을 함께 제공한다.

## 11 심층 기록의 예시

이 절은 특정 유명 제품을 직접 관찰한 결과가 아니라, 이후 실제 관찰 자료를 채울 때의 작성 깊이를 보여주는 설계 예시다. 수치는 의도적으로 발명하지 않았다.

### RPG 장비 비교와 교체

목표는 현재 장비와 새 장비의 차이를 이해하고 잘못된 슬롯이나 대상을 바꾸지 않은 채 탐험으로 돌아가는 것이다.

관찰할 장면은 인벤토리 진입, 목록 이동, 아이템 상세, 현재 장비와 비교, 장착 가능 조건, 확정, 변경 결과, 목록 복귀, 탐험 복귀다. 어떤 스탯이 비교되는지, 장비 변경 시 관련 값이 함께 갱신되는지, 손실과 이득을 색 외의 부호·문구로도 알리는지 기록한다. 필터·정렬·선택·스크롤이 남는지, 마우스와 컨트롤러의 이동이 다른지도 본다.

실측할 항목은 인벤토리 패널의 기준 영역 점유율, 목록 행과 슬롯의 보이는 크기 및 hit area, 선택과 상세 사이 간격, 비교 숫자의 정렬, 글자 확대 시 정보 손실, 비교 창이 다른 주요 정보를 가리는 면적이다. 공식 영상만 확보되면 hit area와 실제 포커스 동작은 미확인이다.

원리 후보는 ‘같은 판단에 필요한 비교 속성을 같은 순서로 제공하고, 선택을 바꾸어도 기준 장비를 잃지 않게 한다’이다. 적용 조건은 여러 후보를 연속 비교하는 과제다. 비적용 조건은 직접 비교가 불가능한 서로 다른 역할의 아이템, 비교 계산의 조건이 숨겨진 경우, 좁은 화면에 전체 표를 강제로 넣는 경우다.

구현 계약은 selected_item, equipped_item, compare_mode, action_eligibility, focus_origin, list_scroll, filter_state를 구분한다. EquipPending 중 중복 입력 처리, EquipFailed에서 원래 데이터 보존, EquipSuccess에서 실제 변경된 속성 알림, 닫기 후 선택 복귀를 정의한다. 모든 게임이 서버 요청형인 것은 아니므로 실제 구조에 맞지 않는 pending을 억지로 추가하지 않는다.

검수 과제는 ‘장착할 수 없는 장비를 고른다’, ‘긴 이름과 많은 속성을 표시한다’, ‘컨트롤러로 비교 후 뒤로 간다’, ‘선택 항목이 갱신 중 사라진다’, ‘글자를 키워도 장착 조건과 결과를 파악한다’다. 통과 여부는 행동과 상태 보존으로 정의하고, 예쁜 화면이라는 평가만 남기지 않는다.

### 반복 학습의 오답과 다음 문제

목표는 응답 결과를 이해하고, 오답의 이유를 확인한 뒤 적절한 다음 활동으로 이동하는 것이다.

관찰할 장면은 문제 읽기, 응답 선택, 제출 전 수정, 제출 중 상태, 정답과 오답 피드백, 힌트·해설, 다시 풀기, 다음 문제, 세션 종료, 복습 큐 진입, 중단과 재개다. 피드백이 정답만 알려 주는지 이유까지 제공하는지, 실수로 다음 문제를 누를 가능성이 있는지, 제출 버튼과 다음 버튼의 위치가 어떻게 바뀌는지 기록한다.

레이아웃 실측은 문제·답안·힌트·피드백·행동 영역의 분리, 긴 지문과 가상 키보드 출현 시 가림, 답안 선택과 정오답 상태의 차이, 피드백 영역의 높이 변화다. 점수·연속 학습일·보상 애니메이션은 학습 내용과 다른 정보 역할로 분류한다.

원리 후보는 ‘응답을 확정하는 행동과 피드백을 읽은 뒤 진행하는 행동을 상태로 구분한다’이다. 조건에 따라 동일 위치의 버튼을 다른 상태로 사용할 수도 있지만, 빠른 반복 입력이 피드백을 건너뛰지 않도록 입력 계약을 정해야 한다. 실시간 속도 훈련에서는 다른 설계가 필요할 수 있다.

구현 계약은 Answering → Submitting → FeedbackCorrect 또는 FeedbackIncorrect → ReviewingExplanation 또는 NextReady를 구분한다. 서버 오류는 오답으로 표시하지 않는다. 응답·진도 저장 성공과 네트워크 전송 대기를 구분한다. 실제 학습 성과는 정답률, 후속 회상이나 전이 과제 등 별도 연구 설계로 확인하며 버튼 클릭이나 체류 시간만으로 결론 내리지 않는다.

### 카드게임의 행동 확정

목표는 카드 비용, 가능한 대상, 효과와 순서를 이해하고 행동을 확정하는 것이다. 손패의 미리보기와 선택, 대상 지정, 취소, 확정, 연출, 최종 게임 상태, 기록을 각각 조사한다. ‘드래그가 된다’만 기록하지 않고 클릭이나 탭으로 대체할 수 있는지, 카드 겹침이 실제 선택 영역을 어떻게 바꾸는지, 카드 효과의 긴 설명과 키워드 도움말을 어떻게 읽는지 확인한다.

웹 콘텐츠에서 드래그를 사용하는 기능은 해당 예외가 적용되지 않는 한 드래그 없는 단일 포인터 방식도 제공해야 한다는 WCAG 2.5.7의 기준을 별도로 검토한다. 키보드 대안만 있다고 이 기준을 자동 통과하는 것은 아니다. [W3C Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

이미 상대에게 공개되거나 게임 상태가 확정된 행동은 취소가 불가능할 수 있다. 이 경우 확정 전에 대상과 비용을 예고하고, 확정 후에 어떤 변화가 일어났는지 설명하는 방식으로 검토한다. 이는 장르의 규칙에 따라 달라지는 설계 제안이다.

## 12 검수 체계

### 검수의 층위

1. 근거 검수: 각 사실·수치·그림의 출처와 관찰 조건이 있는가
2. 구조 검수: 범위 안의 화면·상태·실패·복귀 경로가 누락되지 않았는가
3. 구현 검수: 제안한 토큰과 상태를 실제로 구현할 수 있는가
4. 접근성 검수: 자동 검사와 수동 조작을 함께 수행했는가
5. 사용성 검수: 목표 사용자에게 과제를 주고 성공·실패·어려움을 확인했는가
6. 성능 검수: 관찰 환경과 측정 종류를 구분했는가
7. 유지보수 검수: 버전이 바뀌었을 때 어떤 주장을 다시 확인해야 하는가

### 시나리오 형식

```json
{
  "test_id": "",
  "requirement_ids": [],
  "evidence_or_standard_ids": [],
  "classification": "accessibility|functional|usability|performance|localization",
  "setup": "",
  "input_method": "",
  "given": "",
  "when": "",
  "then": [],
  "measurement_method": "",
  "pass_threshold": null,
  "threshold_origin": "official|project-baseline|task-requirement|not-numeric",
  "result": "not-run|pass|fail|blocked|not-applicable",
  "actual_evidence_ids": [],
  "severity": null,
  "remaining_risk": null
}
```

공식 기준, 프로젝트 목표, 이전 버전 대비 개선 목표를 다른 열에 기록한다. 근거 없이 ‘성공률 90%면 통과’, ‘3클릭 이내’, ‘5명 테스트면 충분’처럼 만능 숫자를 넣지 않는다. 참여자 구성·과제·비교 조건·표본 한계와 통과 기준의 이유를 밝힌다. 사용자 연구가 없으면 전문가 관찰이나 휴리스틱 검토라고 적는다.

### 본편마다 포함할 검수 과제

| 영역 | 예시 과제 | 확인할 결과 |
| --- | --- | --- |
| 초보 | 도움 없이 첫 핵심 작업을 시도 | 다음 행동과 결과를 이해하는지, 막힌 지점을 기록 |
| 숙련 | 같은 작업을 반복 | 불필요한 반복 설명, 선택·필터·위치 손실 여부 |
| 키보드 | 포인터 없이 주요 동선 수행 | 의미 있는 포커스 순서, 가시성, 탈출과 복귀 |
| 컨트롤러 | 화면의 각 메뉴와 동작에 이동 | 방향 기대와 실제 이동 일치, 입력 기호, 되돌아가기 |
| 터치 | 작은 창과 가상 키보드에서 수행 | hit area, 겹침, 가림, 실수와 회복 |
| 상태 | 로딩·빈 데이터·부분 데이터·오류 | 진행 상황, 할 수 있는 행동, 보존과 재시도 |
| 데이터 | 긴 제목·다수 항목·최댓값·값 없음 | 잘림, 정렬, 단위, 숨겨진 중요 정보 |
| 확대 | 브라우저와 앱 글자 크기 변경 | 내용·행동·포커스 손실, 불필요한 양방향 스크롤 |
| 색과 소리 | 색이나 소리 하나의 신호에 의존하지 않고 수행 | 상태·위험·정오답의 대체 표현 |
| 현지화 | 한국어·영어·긴 번역·지원 시 RTL | 줄바꿈, 문장 결합, 방향성, 날짜·숫자·단위 |
| 중단 | 앱 전환·탭 복귀·세션 만료·네트워크 손실 | 저장 상태, 재개 위치, 중복 실행, 데이터 손실 |
| 동작 감소 | reduced motion 또는 게임 설정 적용 | 필요한 정보 유지, 멀미 유발 움직임 대안 |

지원하지 않는 입력 방식을 자동 실패로 적지 말고 제품 범위와 접근성 요구에 비추어 판단한다. 반대로 범위를 좁힌다는 이유로 주요 사용자에게 필요한 경로의 결함을 숨기지 않는다.

### 막아야 할 핵심 결함

- 핵심 작업을 마칠 수 없음
- 중요한 정보가 잘리거나 다른 화면 아래 숨음
- 취소·복귀가 없어서 사용자가 갇힘
- 무엇을 바꾸는지 모른 채 중요한 행동이 실행됨
- 실패 후 입력이나 진행 상태를 불필요하게 잃음
- 실행 중 반복 입력으로 중복 주문·중복 행동 발생
- 시각 상태와 실제 데이터 상태가 불일치
- 특정 입력이나 보조기술로 핵심 경로를 사용할 수 없음

치명적 기능·접근성 결함은 평균 점수로 상쇄하지 않는다. 미확인 상태는 통과로 처리하지 않는다. 자동 접근성 검사 통과만으로 전체 적합성이나 사용성을 인증하지 않는다.

## 14 성능과 쾌적함을 다루는 방법

쾌적함을 ‘부드럽다’, ‘깔끔하다’ 같은 감상으로 끝내지 않는다. 다음 요소를 각각 관찰한다.

- 입력을 받았다는 피드백이 있는가
- 진행 중 상태와 완료 상태를 구분할 수 있는가
- 기다리는 동안 다음 행동을 알 수 있는가
- 레이아웃 변화로 읽던 내용이나 누르려던 버튼이 움직이는가
- 화면 전환 후 이전 문맥을 잃는가
- 반복 연출이 주 작업을 방해하는가
- 콘텐츠 로딩 순서가 핵심 과제에 맞는가
- 오프라인과 재접속에서 상태가 일치하는가

웹은 Core Web Vitals와 과제별 실제 완료 시간을 구분한다. 게임은 목표 하드웨어·해상도·UI 배율·장면 복잡도를 정한 다음 프레임 시간 분포, 입력에서 피드백까지의 지연, 메뉴 전환, 첫 플레이 가능 시점, 중단 후 복구를 기록한다. 게임·학습 영상·일반 웹의 모든 반응을 같은 수치 하나로 평가하지 않는다. 목표 FPS나 시간 예산은 프로젝트의 하드웨어와 장르에 맞게 정한 값이라고 표기한다.

측정 환경을 통제할 수 없는 공개 영상의 프레임 드롭이나 화면 변화만으로 실제 제품 성능을 단정하지 않는다. 재생 환경, 영상 편집과 인코딩이 원인일 수 있다.

## 15 AI 슬롭을 막는 출고 기준

다음 중 하나라도 있으면 완성 매뉴얼로 처리하지 않는다.

- 사례 이름만 나열하고 무엇을 관찰했는지 없음
- 홈 화면 한 장만 보고 전체 UX를 설명
- 서로 다른 플랫폼과 단위를 섞어 숫자를 비교
- 출처 없는 버튼 크기·색상 비율·레이아웃 황금비율 제시
- 실제 관찰과 권장안을 구분하지 않음
- ‘직관적’, ‘몰입감’, ‘깔끔함’ 같은 형용사만 있고 행동 근거가 없음
- hover만 있고 키보드·터치·컨트롤러 상태 없음
- 성공 화면만 있고 로딩·오류·취소·복귀 없음
- 같은 계층의 모든 카드에 같은 강조를 주면서 이유를 설명하지 않음
- 대조 사례 없이 한 제품을 정답처럼 복제
- 긴 실제 데이터, 빈 데이터, 번역, 확대 시험 없음
- 픽셀 배치만 제공하고 상태·조건·데이터 관계 없음
- 유명함을 사용성의 인과 증거로 사용
- 측정하지 않은 전환율·만족도·학습 효과를 지어냄
- 공식 권고와 의무 수준을 혼동

반대로 시각적 유행 자체를 금지하는 목록으로 만들지도 않는다. 카드, 그라데이션, 어두운 화면, 둥근 모서리, 아이콘, 넓은 여백은 목적과 맥락에 맞으면 사용할 수 있다. 선택 이유와 대가, 실제 상태 구현이 없는 것이 문제다.

출고 시 판정은 다음 중 하나다.

- 조사 초안: 핵심 증거가 부족함
- 문헌 기반 비교판: 공식 문서·영상 중심이며 실측 제한을 표시함
- 관찰 검증판: 범위 내 실제 화면과 동선 증거를 확보함
- 구현 검증판: 규칙을 프로토타입에 적용하고 시험 결과를 첨부함
- 사용자 검증판: 목표 사용자의 과제 수행 결과와 연구 한계를 첨부함

한 단계의 성공이 다음 단계의 성공을 의미하지 않는다. 사용자 검증을 하지 않은 매뉴얼은 이를 한 것처럼 제목을 붙이지 않는다.

## 16 조사에서 적용까지의 작업 순서

1. 본편 하나와 핵심 과제를 정한다
2. 목표 사용자·플랫폼·입력·시간 압박·실수 비용을 적는다
3. 과제가 비교 가능한 사례 2~4개를 선정한다
4. 공식 자료를 확인하고 직접 관찰 가능한 경계를 정한다
5. 세션 환경을 저장한다
6. 화면 지도와 정상 동선을 기록한다
7. 상태·취소·오류·복귀·중단 경로를 조사한다
8. 원본 증거를 보존한 채 주석과 측정표를 작성한다
9. 같은 과제끼리 대조하고 다른 선택의 이유와 비용을 적는다
10. 원리마다 근거·적용·비적용·한계를 쓴다
11. 프로젝트용 토큰과 상태 계약으로 바꾼다
12. 접근성·현지화·성능·경계 데이터로 검수한다
13. 필요하면 목표 사용자 시험을 하고 과도한 일반화를 수정한다
14. 변경된 사실과 미확인 항목을 남긴다

관찰 대상 서비스에서 실제 구매·제출·데이터 삭제·외부 연락 등을 하지 않고 확인 가능한 경계까지 조사한다. 이를 넘어서는 조사가 꼭 필요하면 구체적인 행동과 목적에 맞는 권한을 먼저 확인한다. 오류를 보기 위해 운영 서비스에 해를 주는 입력·부하·파괴적 테스트를 하지 않는다.

## 18 사용자에게 먼저 보여줄 요약 목차

게임은 RPG·카드와 덱빌딩·퍼즐과 캐주얼·전략과 관리·실시간 액션으로 나눕니다. 웹게임은 별도로 공통 환경을 정리해서 각 장르와 조합합니다.

웹은 쇼핑·정보 탐색·강의·콘텐츠와 커뮤니티·업무 도구·예약과 신청으로 나눕니다. 앱은 반복 학습·미디어·개인 생산성·생활 서비스의 작업 방식에 맞춰 구분합니다.

각 매뉴얼은 실제 사례 2~4개를 같은 기준으로 깊게 조사합니다. 화면 전체 구조, 버튼과 메뉴의 크기·위치·비율, 색상의 역할, 정보 구분, 처음부터 완료·오류·취소·복귀까지의 동선을 기록합니다. 관찰한 사실, 직접 잰 수치, 공식 기준, 해석과 권장안은 분리합니다.

마지막에는 바로 제작에 사용할 수 있는 레이아웃 규칙·디자인 토큰·동작 상태·검수 과제를 붙입니다. 사례를 축적할 때도 같은 양식을 사용해 장르와 목적에 맞는 원리를 비교할 수 있게 합니다.


## 19 사용자 검수 후 스킬화하기 위한 모듈

최신 요구에 따라 이 매뉴얼은 조건을 받아 설계 결정을 도출하고 예시로 검수할 수 있는 수준으로 모듈화한다. 현재 산출물은 사용자 검수 전 초안이다. 실제 개인 스킬을 설치하거나 등록하지 않았으며, 예시를 확인한 사용자의 수정 요청과 승인 범위를 먼저 반영한다.

실행 흐름은 M01 조건 수집 → M02 용도·플랫폼 분류 → M03 근거 연결 → M04 조건별 설계 결정 → M05 토큰·레이아웃·동선·상태 계약 → M06 예시와 검수 → M07 사용자 승인이다.

입력은 주목적, 용도, 플랫폼을 필수로 받는다. 입력 방식·숙련도·콘텐츠 양·시간 압박·행동의 취소 가능성·실제 창 크기·언어·글자 배율·저장 요구는 해당 결정에 필요할 때 추가한다. 모르는 조건을 false나 0으로 간주하지 않는다. 디자인을 바꾸는 누락 조건만 질문하고, 그 외에는 가정이나 미확인으로 표시한다.

규칙 하나는 ID, 적용할 본편, 필요한 조건, if 조건, then 설계 결정, 대안, 비적용 조건, 토큰·레이아웃·동선·상태, 검수 과제, 출처 ID, 실제 사례 증거 ID, 예시 ID를 갖는다. 프로젝트 권장안을 공식 의무로 바꾸지 않는다. 현재 실제 사례 증거 ID가 빈 규칙은 사례로 검증되었다고 표현하지 않는다. ID가 연결된 규칙도 case_evidence_support의 제한된 절만 뒷받침하며 규칙 전체의 검증을 뜻하지 않는다.

JSON의 조건 문장은 사람이 읽는 의사결정 계약이다. 실행 코드나 만능 자동 설계 엔진이라고 주장하지 않는다. 규칙을 적용할 때는 조건을 확인하고 어떤 대안을 배제했는지 남긴다.

### 측정 가능한 검수 계약

각 검수는 Given·When·Then을 갖고 결과를 미실행·통과·실패·차단·해당 없음으로 기록한다. 예를 들어 ‘오답 화면이 직관적이다’ 대신 ‘제출을 연속 눌러도 동일 attempt가 한 번만 기록되고 현재 문제의 피드백이 유지된다’를 검사한다. ‘장비 화면이 편하다’ 대신 ‘비교를 닫아도 선택 항목·필터·정렬·스크롤·포커스 문맥이 보존된다’를 검사한다.

치수의 프로젝트 목표는 공식 최소값이나 실제 사례 측정값과 분리한다. 구조 검사의 합격은 JSON 필드와 참조가 맞는다는 뜻이며, 실제 예시 UI의 검사나 사용자 시험이 완료되었다는 뜻이 아니다.

사이트의 구현 요소에는 규칙 ID를 연결하고, 규칙의 문서·근거·예시 상태·검수 결과를 서로 찾아갈 수 있게 한다. 연결된 규칙이 전부 구현되었다는 뜻은 아니므로 미구현과 선택 범위 밖 항목을 표시한다. 쇼핑의 실제 결제와 강의의 영상·영구 진도 저장은 해당 기능을 구현·검증하기 전에는 예시의 완성 범위로 포함하지 않는다.

## 20 사례 근거 연결 현황

RPG·카드게임 조사와 브라우저 게임·앱 조사에서 직접 뒷받침하는 절만 규칙에 연결했다. case_evidence_registry.json은 제품·출처·관찰 범위·파일·미확인 조건을 모으고, 규칙의 case_evidence_support는 정확히 어느 절을 뒷받침하는지 기록한다.

현재 제품 14개, 사례 근거 레코드 24개를 색인했다. 30개 규칙 중 16개에 부분 근거가 연결되었고 14개는 미연결이다. 직접 데스크톱 관찰 사례는 8개이며 공식 문서·이미지·영상 중심 사례는 6개다. 모든 34개 acceptance는 미실행 상태를 유지했다. JSON과 근거 파일 참조의 정합성만 확인했으며 실제 예시의 시험 결과를 통과로 바꾸지 않았다.

FFXIV의 비교 화면은 나란한 비교 기준·속성 순서·일부 증감 부호를 뒷받침한다. 비교를 닫은 뒤의 scroll·focus 보존은 미확인이다. SNAP 패치는 임시 행동·턴 제출·조건부 취소의 경계를 뒷받침하지만 현행 모든 모드와 네트워크 경합은 미검증이다.

2048의 직접 조작은 실패·재시작·현재 점수와 최고 기록의 구분을 뒷받침한다. Lichess는 단원과 현재 문제·완료 기록의 복귀를 뒷받침한다. Duolingo 공식 이미지는 피드백·선택 설명·Continue의 시각적 구분을 뒷받침하지만 연속 입력 가드·실제 복귀·통신 실패를 확인한 것은 아니다.

웹 쇼핑·정보·강의 사례의 원고와 관찰 로그 연결을 완료했으며, 모든 신규 연결에도 같은 부분 근거 경계를 적용했다. IKEA는 필터 적용·해제, Apple은 의존 옵션과 변경 비용의 검토, Wikipedia는 문서 내 이동·복귀, MDN은 관련 문서 복귀의 문맥 유지와 픽셀 차이, Khan은 목록 접기와 영상 공간 재배분을 뒷받침한다. Coursera 공개 모듈 탐색 자료는 색인했으나 강의실 진도 복원이나 평가 제출의 직접 증거로 전용하지 않았다. 근거를 연결했다고 현재 화면의 사용성·효과·공식 적합성을 인증하지 않는다.


### 근거 연결의 최종 경계

14개 제품은 본편 전체 완성을 의미하지 않는다. 직접 데스크톱 관찰 8개와 공식 자료 중심 6개를 구분한다. 공식 기준 출처 21개는 제품 사례 출처와 다른 목록이다.

24개 사례 근거 레코드 중 23개가 규칙의 일부 절에 연결되었고, Coursera의 공개 과정·모듈 탐색 레코드 1개는 현재 규칙에 억지로 연결하지 않았다. 연결된 16개 규칙은 부분 근거 상태이고 나머지 14개는 미연결이다. 스크롤과 포커스의 완전 복원, 모든 입력의 동등성, 네트워크 회복, 실제 모바일·확대·보조기술·성능·동작 감소 등의 빈칸을 숨기지 않았다.

34개 acceptance는 전부 not_run을 유지한다. 예시 페이지의 코드 작성이나 게시가 실제 브라우저 조작 검수·사용자 검수를 대신하지 않는다. 이 단계에서는 등록·설치·사이트 코드 변경을 하지 않고 문서와 JSON 참조만 보완했다.

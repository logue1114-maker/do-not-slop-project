# Future ordinary-request versus framework experiment

**Status: protocol only. No new paired output, Before/After improvement or causal result has been generated.** Authored hypothetical application scenarios are not experimental arms.

## Scope and freeze

Name one actual task/flow, target revision and acceptance question. Freeze the same source, licensed/permitted assets, behavior, task complexity, model/version, available tools, total budget, launch environment, viewport/DPR/zoom, input, locale/text scale, state fixture, camera/background and capture milestones. Record unknown calibration instead of claiming matched pixels.

Use a reasonable ordinary request of the same goal and specificity appropriate to an ordinary user. The framework arm receives the extra structured guidance as the intended intervention. Do not deliberately weaken the ordinary task, omit its necessary protected behavior or give one arm extra assets/hidden advice/tool budget.

Preserve prompts, original source and first outputs from both arms. Capture seeds/model nondeterminism where the runtime exposes them; do not fabricate reproducibility. If several runs are performed, retain failures and report the selection rule rather than choosing only a favorable pair.

## Observe before repair

Capture actual full entry/ready/play/decision/result/return and native state/component crops under the frozen fixture. Run identical available input and protected-behavior checks. Inspect composition, silhouette/length, face/rim/body or valid flatness, type/glyph, layout/rank, actual state, material/light/texture and scene relation separately.

Classify each finding as observed defect against an applicable requirement, conditional proposal, deliberate valid alternative or user taste. Keep rule applicability and unknown conditions visible. Screenshot pixel evidence cannot establish input/hitbox; source/hash tests cannot establish craft.

## Repair accounting

If an arm needs repair, preserve its first output and list the repair prompts, tool time, human intervention and actual revised captures. Either allocate an equivalent repair policy to both arms or clearly report unequal treatment. Do not hand-retouch the framework result and present it as an untouched generated output.

## Reporting and stopping

Report specific improvements and regressions at the named revision/state, actual parity/input results, unfinished/blocked states, rights and calibration limits, user review and any excluded runs. Separate first-pass output from repaired outcome. A single pair supports only that scoped comparison; it cannot prove universal genre superiority, measured usability or productivity.

Stop when the frozen checks and reporting artifacts are complete, the user cancels, a material scope/authority requirement blocks progress, or the declared observation cannot be obtained. A failed or unchanged output is still an outcome to preserve. Publication, game mutation and participant testing require their own applicable authorization.

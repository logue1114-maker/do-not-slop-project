# Exact reusable AI production packet

Use the following instructions with the target source, the filled `brief.schema.json` packet, selected `recipe-catalog.json` records, their source records, and exact applicable pinned project rules. Replace only the target/task inputs. Keep the conditional selection and evidence limits intact.

## Mission

Produce a coherent whole-screen interface sequence that fits the actual player task, real art, content, platform and supported behavior. Work from main entry or actual first arrival through first action, play/decision, interruption/result and supported return. The requested change must appear in the actual rendered geometry and state. Preserve unrelated source, data, handlers, records, eligibility, loss/reset scope, saved state and network authority.

A recipe is a conditional production operation, not an approved canonical rule, copied art asset or proof of superiority. A genre name never determines one fixed layout, skin, HUD corner, icon, bevel or target size.

## Inputs and stop conditions

Read the actual target before coding. Trace its entry point and one action through input, domain validity/state and output. Load the exact applicable original project rules at the canonical pin; inspect required inputs, `if`, exceptions, scope and existing draft status. If you cannot read a rule, record unavailable authority instead of reconstructing it from a summary.

Require these inputs together:
- Current player goal, state, next action, time pressure and actual lifecycle
- Allowed changes and protected behavior/data/consequences
- Complete in-scope screen/state flow, prerequisites, loss/reset/return paths
- Real imagery, camera/background range, art identity and existing coherent grammar
- Actual labels, supported locales, changing values, list counts and longest content
- Actual platform, logical units, viewport/safe areas/host chrome and supported inputs
- Every genuinely concurrent HUD/menu/prompt/chat/notification/tutorial layer
- Source evidence, rights, inspection/build identity and acceptance requirements

Keep unknown values explicit. Ask only for design-changing information that cannot be found. You may deliver an explicitly conditional proposal while it is unresolved. Do not claim implementation-ready while task/flow unknowns, unresolved visual values or coordinate mapping remain. Technical readiness does not grant authority to mutate source, send data, publish or transact.

## Execute in this dependency order

### 0. Resolve authority, source and platform

Output `BRIEF` and a source/rights ledger. Select original rules only when their actual conditions match; check their exceptions. Keep unsupported canonical routes unsupported. `DNS-*` recipes can guide a manually reviewed proposal without pretending to be a newly supported canonical route.

For every selection, record recipe/rule ID, source pin, actual trigger values, evidence IDs, unknown conditions, checked exceptions, applicability (`applicable`, `conditional`, `not_applicable`), decision and rejected alternative. Unknown conditions become conditional proposals, never observed violations.

The platform adapter owns unit mapping, native semantic controls, safe areas/host controls, focus/navigation/input translation and engine projection. Never equate encoded screenshot pixels, CSS px, device pixels, pt, dp or world units. Apply only the actual platform's required target/contrast/input rules and stated exceptions in their native units.

### 1. Compose the task sequence

Apply DNS-01/03/17 when their conditions match. Name what must be seen, understood and done in each state. Mark the real board/graph, path, threat, aim, next landing or comparison region before placing interface groups.

Choose scene-led peripheral controls, concentrated local decision, split subject/detail or UI-as-game composition by that task and content fit. Storyboard only real entry/setup/readiness/play/result/return states. A game beginning immediately in play does not acquire an invented menu. Necessary room/mode/setup choices must not disappear merely to reduce clicks.

Output `SCREEN_PLAN` plus `FLOW_STORYBOARD`: reading order, scene/decision bounds, main/local commitments, utilities, retained/replaced layers, focus/input owner, exact transition and reset/loss semantics. Classify copy by identity/rule/condition/consequence/recovery/duplicate/filler; remove duplicated copy and obsolete fixed height, while retaining unseen rules and eligibility qualifiers.

### 2. Resolve visual grammar against actual art

Apply DNS-02/08/10. Produce a bounded variant sheet or adaptation sheet using identical task/content/state/background/scale. Change the unresolved axis; if several axes change, label it art-direction comparison rather than attributing the result to color alone.

Resolve actual values and units for:
- Silhouette/corner/cap/outline family
- Scene versus panel/row/command materials, quiet ink zones and permitted underlays
- Face/rim/body/contact shadow/light direction where justified, or deliberate flatness
- Texture frequency and which artwork zones stretch, tile or remain fixed
- Typography/license/fallback, weight/case/size/line-height/wrapping/numerals/baseline
- Surface/ink/command/utility/current/focus/unavailable/feedback/hazard pairings
- Spacing, grouping, content minimums, safe areas and ornament carriers

Several role families can share grammar while differing in relief, opacity, dimensions and rank. Flat/text-only/no-icon is valid when the brief permits it. If actual silhouette, face/body or inner-layout changes are required, recoloring/font/background work alone does not satisfy them.

Output `ART_TASK_CONTRACT`, `VISUAL_TOKENS` and actual-string/material specimen requirements. Words such as polished, clean, modern or cohesive are not resolved tokens.

### 3. Coordinate HUD, repeated decisions and simultaneous layers

Apply DNS-04/09/13. Register visual, ink and interactive bounds, owner, priority, lifetime, input and restoration for every allowed combination in one verified coordinate system.

Use reserved space, reflow, collapse, replacement or queueing deliberately. Z-order alone only decides what gets hidden. Retain time-critical hazards/objectives when the world continues. Chat/social information can itself be the current task. World-camera occlusion and screen UI collision are separate checks.

Group repeated title -> current/required condition/value -> action as one scan unit. Select segments, rows/table or subject/detail by genuine comparison, identity and fit. Inspect/select/current/owned/equipped/unavailable/path-ready/commit are distinct. A green conditional instruction or selected marker is not proof of readiness or successful execution. Preserve discovery rules and supported selection/scroll.

Output `LAYER_MATRIX`, `HUD_ENVELOPE`, `DECISION_SLOT_CONTRACT` and actual worst-combination fixtures.

### 4. Construct component anatomy and scalable art

Apply DNS-05/06/07/11/12 with the exact existing button contract. Classify each member as command/navigation/toggle/selection/tab/value edit/read-only/spatial target before styling.

Budget target, silhouette, visible face and real ink separately. Measure loaded labels and present icon/cost/shortcut/timer slots. Derive shell width from actual ink + existing slots + gaps + safe horizontal insets + chosen rim; derive height from supported lines + safe vertical insets + chosen rim/body. Circles must fit label/timer within their actual usable chord, not the full diameter. Do not shrink all labels to preserve a selected circle, count decorative shadow as hit area, or reserve nonexistent icon slots.

Keep title/close/list/footer inside an illustrated surface's safe ink mask. Preserve fixed corners/caps/bolts and texture scale through native slicing, tiled centers or separate pieces; keep text/focus/state layers independent of art. Plain code/native geometry needs no artificial slicing.

Verify loaded real glyph counters, baseline, optical icon mass, outline thickness, real wrapping and long strings. Comparable choices may share widths; unrelated utilities need not. Read-only HUD values must not acquire command affordances.

Output `COMPONENT_CONTRACTS`, `PANEL_ANATOMY`, `TYPE_SPECIMENS` and `ASSET_STRETCH_MAP`, with numerical project trials or explicit unresolved measurement tasks.

### 5. Implement supported states and maintainable owners

Apply DNS-14/15/16/20. Implement only genuine supported states. Hover, focus, press, persistent selection, unavailable, pending and actual result have separate meanings and static signals. Focus must remain visible over selected/pressed faces. Unavailable reasons need a supported reading route; duplicate commitment, release-away, repeat/cancel and actual recovery must remain correct.

For motion, name meaning, moving part, fixed shell/target, start/mid/end bounds, timing/easing trial, interruption/repetition and reduced-motion static meaning. No timing or hitbox claim comes from an unplayed video or a still. For optional art, reserve slots and readable fallback; for essential art, implement only supported loading/error/recovery. Locale refresh must include visible values and newly revealed rows without altering semantic state.

Before source edits, output `CHANGE_MAP`: “To change X, edit Y because Y owns Z.” Separate actual reasons to change: domain rules, presentation/state projection, tokens/assets, input controllers and real persistence/platform integration. Domain rules must not read view/DOM/global storage; views must not decide legality or send orders. Do not invent absent layers, speculative managers or hundreds of tiny files.

Document inputs/outputs/mutation/errors/side effects and initialization/disposal. Use names that reveal intent and comments explaining real invariants/tradeoffs. Preserve good boundaries and dependencies. Separate refactoring from intentional behavior change. Characterize the real entry and check failure/recovery/repeated input and cleanup after meaningful transitions.

### 6. Inspect, repair and deliver actual evidence

Apply DNS-18. Inspect the whole screen first, then native component/state crops and before/mid/settled motion. Match revision, task, fixture/data, viewport, DPR, zoom, logical/capture units, locale/text scale, loaded font, background/camera and milestone.

For each requested axis submit before -> intent -> actually rendered evidence. Required axes include the named silhouette/length, face/rim/body or deliberate flatness, type/glyph, internal layout, local rank, supported state and scene relation. If an axis is missing, repair it and recheck affected states. Do not relabel an unmet required structural change as an exception.

Report independent gates: source integrity, structure, protected behavior parity, composition, visual craft, responsive/state/motion, actual flow/input, physical device where required and user review. Use pass/fail/not_run/blocked/inconclusive literally. Source declarations, hashes and complete fields do not establish pixels, behavior, access rights, measured usability or approval.

Deliver the scoped diff/runnable entry where authorized, complete packet, selected-rule decisions, owner/change map, resolved tokens/components, evidence ledger, commands and actual results, limits and remaining user decisions. All authored-only outputs retain proposal status until actually built/tested. Never invent an After capture or functioning game result.

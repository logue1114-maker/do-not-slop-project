# 게임 UI/UX 심층 매뉴얼 조사: RPG편 · 카드게임편

조사일: 2026-10-03 UTC. 공개 공식 문서·개발자 글·공개 이미지 기반. 게임 실행·설치·로그인·결제·사용자 컴퓨터 접근은 하지 않았다. 이미지 관찰은 dot 클라우드 브라우저에서 수행했다.

## 증거 구분과 읽는 법

- **문서 확인(D)**: 공식 문서가 동작을 설명한다. 실제 플레이로 재현했다는 뜻이 아니다
- **화면 관찰(V)**: 이 조사에서 직접 열어 본 공개 게임 이미지에서 관찰했다
- **해석(I)**: 확인한 사실에서 도출한 UX 판단. 사용자 테스트 결과나 개발자의 의도라고 단정하지 않는다
- **미확인(U)**: 해당 상태·입력·버전에서 확인할 근거가 부족하다. 다음 조사에서 검증해야 한다
- 공식 사이트 갱신일과 이미지가 촬영된 게임 빌드는 별개다. 옛 개발 블로그는 현재 동작의 증거로 승격하지 않는다
- 메뉴 깊이는 '지금 있는 화면에서 목적 상태까지 추가로 거치는 의미 있는 선택 단계'로 센다. 클릭 수, 키 입력 수, 애니메이션 시간과 구분한다. 아래 단계 수는 문서에 나온 경로의 모델이며 실측 시간은 없다
- 크기 수치는 원본 이미지 파일의 해상도다. 게임 UI 스케일·디스플레이 DPI·실제 터치 목표 크기를 뜻하지 않는다. 색 면적 비율과 픽셀 규격을 측정하지 않았으므로 생성하지 않는다

## RPG편

### 사례 R1. FINAL FANTASY XIV: 높은 정보 밀도를 '작업별 경로'로 다루는 MMORPG

#### 증거 범위

공식 Game Manual / UI Guide를 읽었다. Game Manual 페이지에 표시된 최근 갱신일은 2026-09-08이다. 장비 비교 이미지는 원본을 직접 보았다. 공식 이미지의 게임 빌드는 명시되지 않아 최신 클라이언트의 동일 화면이라고 단정하지 않는다.

#### 1. 정보 구조: 하나의 메뉴보다 병렬 진입점

**D** 주요 분류는 Character, Duty, Logs, Travel, Party, Social, System이다. 퀘스트 HUD는 제목 선택 시 Journal, 목표 선택 시 Map으로 연결된다. 기술 관리는 Character → Actions & Traits, HUD 조정은 System → HUD Layout에 있다. [R1-01]

**I** 구조를 '메인 메뉴 7개이므로 7개가 적정'으로 모사하지 않는다. 중요한 특징은 현장 단서에서 상세 정보로 이어지는 지름길이다. 퀘스트 제목과 장소를 다른 목적지에 연결해 '무엇을 할지'와 '어디로 갈지'의 탐색을 나눈다. 새 RPG에 적용한다면 HUD→상세→지도 간 같은 퀘스트 ID·선택 상태를 유지하도록 명세해야 한다. 이 마지막 상태 보존은 FFXIV 실제 복귀 동작을 확인한 주장이 아닌 설계 제안이다.

#### 2. 탐험·지도·퀘스트: 읽기와 이동을 분리하지 않기

**D** Map은 Travel 또는 미니맵에서 열 수 있다. 지도 자물쇠를 켜면 Escape/취소로 닫히지 않지만 우상단 닫기 버튼은 남는다. 퀘스트는 중요도·유형에 따라 아이콘을 달리 쓰며, 진행 요건을 충족하지 못한 붉은 아이콘은 Duty List나 Journal에서 원인을 확인하도록 안내한다. [R1-02][R1-03]

**I** 지도 잠금은 '뒤로'의 전역 규칙보다 이동 중 참조를 우선한 예외다. 효용은 지도 재열기 비용 절감이고 위험은 '취소가 고장 났다'는 오해다. 자신의 제품에서는 잠금 상태를 모양·라벨로 표시하고 해제 경로를 유지해야 한다. 붉은 아이콘만 있고 이유·다음 행동이 없다면 오류 설명으로는 부족하다. 장소에 도달했는데 높낮이·조건 때문에 완료되지 않는 경우는 별도 상태로 설계해야 한다.

#### 3. 전투 HUD·스킬: 입력장치에 맞춘 작업 공간

**D** 일반 핫바는 끌어 넣기와 잠금 기능을 제공한다. Cross Hotbar는 트리거와 방향/액션 버튼 조합으로 실행한다. 기술을 등록할 때 게임패드는 Hotbar Palette를 열고 사용할 조합을 누르며, 마우스는 아이콘을 직접 끌어 넣을 수 있다. [R1-01][R1-04]

**I** 같은 기능을 포인터와 패드에 같은 제스처로 강요하지 않는다. 실행 배치가 물리적 버튼군과 대응하므로 기억과 재인식이 함께 작동한다. 반면 많은 레이어·세트 전환은 현재 활성 세트 착오를 낳는다. 이동 중 왼손 방향 입력과 공격 조합이 경쟁하는지도 검증해야 한다. 이것은 미실시 테스트 항목이며 플레이 난이도 평가가 아니다.

**D** HUD 편집은 요소 선택, 위치/크기/표시/투명도 변경, 저장 순서다. 선택 요소는 금색 외곽, 숨김 라벨은 보라색이며 4개 기본 슬롯 간 복사가 가능하다. 패드는 오른쪽 스틱으로 위치를 옮기고 스틱 클릭으로 크기를 순환한다. [R1-05]

**I** 커스터마이징은 전문가에게 선택권을 주지만 초보 기본값의 책임을 없애지 않는다. 작은 스크린에 맞추려고 모든 요소를 축소하면 문자와 타깃이 동시에 작아진다. 중요한 경고의 최소 크기, 오버랩 감지, 초기값 복귀, 역할별 예시 프리셋을 별도 검토해야 한다.

#### 4. 인벤토리·장비 비교: 기억 부담을 나란히 보기로 바꾸기

**D** 인벤토리는 Character Configuration → Item Settings → Inventory Settings에서 Expanded/Open All을 선택할 수 있다. Open All은 탭 전환 없이 모두 보도록 한다. 장비의 컨텍스트 메뉴에서 Item Comparison을 열며, 상인·Market Board에서도 비교 기능을 쓸 수 있다. [R1-06][R1-07]

**V** 공식 비교 이미지(896×512)에는 왼쪽 현재 장비, 오른쪽 선택 장비가 같은 열 구조로 놓인다. 이름·아이콘, 피해/자동공격/딜레이, Item Level, 조건, 보너스, 가격 정보 순이다. 오른쪽 피해 수치 옆에 녹색 '(+2)'가 보인다. 하단 중앙 Close와 품질 비교용 Ctrl 안내가 있다. 어두운 중성 바탕과 가는 구획선 위에 읽을 내용을 올린 고밀도 표이며, 아이템 그림은 식별용의 작은 영역이다. [R1-V1]

**I** 개선점은 단순 '녹색 = 더 좋음'이 아니라 비교 대상·기준·차이를 같은 시야에 두는 것이다. 색 외에도 부호가 있어 일부 의미가 중복된다. 그러나 이 스크린샷에서 증가 표시가 없는 보조 능력치도 보이므로 모든 줄에 자동 차이가 있다고 일반화할 수 없다. 전체 전투 효율을 단일 아이템 레벨이나 녹색 하나로 판단하게 만들면 빌드별 선택을 왜곡할 수 있다.

**경로 모델** 인벤토리/상점 목록 → 아이템 컨텍스트 메뉴 → 비교 창 → Close → 출발 맥락. 비교 진입의 의미 단계는 2개다. Close가 직전 목록의 스크롤·초점을 정확히 보존하는지는 **U**다. 자료가 없어 '3클릭으로 장착 완료' 같은 표현은 쓰지 않는다.

#### 5. 상점·복귀·실수 방지

**D** Market Board는 이름/카테고리 검색으로 품목을 찾고, 품목의 History에서 이전 거래 가격·수량·구매자·일자를 볼 수 있다. [R1-08][R1-09]

**I** 가격 검토와 장비 검토를 구매와 분리한 점은 판단 도구로 가져올 수 있다. 그러나 실제 구매 확정, 소지금 부족, 품절/동시 판매, 실수 구매의 복구와 취소, NPC 상점에서 닫은 뒤 재진입 시 상태 보존은 **U**다. 이를 사례의 장점으로 채워 넣지 않는다. 실제 돈을 쓰는 상점에는 게임 내 재화 거래와 다른 총액·환불·과금 안내가 필요하다.

#### 따르지 말아야 할 조건

- 단일 캐릭터·소수 스킬 액션 RPG에 MMORPG 전체 메뉴와 채팅·파티 밀도를 그대로 이식하지 않는다
- 패드 지원이라는 이유로 키보드 기능 수를 줄이지도, 모든 창을 가상 커서로만 다루게 하지도 않는다
- Open All을 모바일 인벤토리의 기본값으로 모사하지 않는다. 정보가 한 번에 보이는 것과 손가락으로 구별해 누를 수 있는 것은 다르다
- 커스터마이징 사용자가 많다는 사실만으로 초기 UI가 좋다고 결론 내리지 않는다. 본 조사는 사용률·완료 시간·오류율을 측정하지 않았다

#### 다음 실증 체크

신규 사용자/숙련 사용자, 키보드·마우스/게임패드, 좁은 화면/큰 화면을 나누어 (1) 퀘스트 위치 찾기, (2) 전투 중 자원/타깃 상태 파악, (3) 두 장비의 차이 설명, (4) 비교 취소 후 원래 품목으로 복귀, (5) HUD 편집 후 원상복구를 시험한다. 완료율, 잘못 선택한 아이템/대상 수, 의미 있는 메뉴 전환 수, 비교 정확도, 되돌리기 성공률을 기록한다. 임의 목표 수치를 기존 게임의 실측치인 것처럼 쓰지 않는다.

### 사례 R2. Diablo IV: 전투 가시성·반복 관리·다중 입력을 동시에 풀기

#### 증거 범위와 시점

이 사례는 한 빌드의 완전한 UI 감사가 아니다. 2020년 개발 중 UI 의사결정, 2023년 출시 전 접근성 안내, Vessel of Hatred 출시와 함께 제공된 길찾기 안내, 2026년 3.0 계열 패치의 오류 수정 기록을 분리해 읽었다. 직접 관찰한 스킬 화면은 명확히 **WORK IN PROGRESS**가 적힌 2020년 자료다. 최신 스킬트리 모양이나 현재 메뉴 깊이의 근거로 쓰지 않는다.

#### 1. 인벤토리: 관리 자체가 재미인지 먼저 결정

**D·역사 자료** UI 책임자 Angela Del Priore는 2020년 글에서 인벤토리 관리가 플레이를 끊지 않도록 아이템 크기 퍼즐을 되살리지 않겠다는 방향을 설명했다. 작은 아이콘의 회화적 표현을 재검토하고, 배경 채도를 낮추며 희귀도를 테두리 장식으로도 나타내려 했다. [R2-01]

**I** 이 결정의 재사용 단위는 '모든 게임은 동일한 인벤토리 칸'이 아니라 **관리의 역할**이다. 자원 배치가 핵심인 생존 게임에서는 공간 퍼즐을 제거하면 의사결정도 지워진다. 반복 전리품 처리 RPG에서는 아이템의 모양을 맞추는 비용보다 비교·보관·판매의 판단 비용을 줄이는 편이 목적에 맞을 수 있다. 이 비교는 설계 추론이며 해당 변경이 유지율을 높였다는 데이터는 없다.

**설계 명세로 옮기기** 획득 → 신규 표시 → 현재 장비와 비교 → 보관/장착/판매/분해 후보 지정 → 결과 피드백 → 원래 탐험 상태를 각각 정의한다. 일괄 동작에서는 개수·대상·되돌릴 수 있는 범위를 함께 보여준다. **U** 이 조사에서 Diablo IV의 최신 판매·분해 확인 모달, 구매 취소/되사기, 필터 상태 보존을 직접 검증하지 않았다.

#### 2. HUD 위치: 중앙 비우기만으로 정답이 되지 않는다

**D·역사 자료** 개발자는 좌하단 액션 바가 중앙 전투 공간을 확보한다는 목적이었으나 사용성 테스트·피드백에 따라 PC 기본을 하단 중앙으로 되돌리며, 시청 거리에 따른 선호 차이를 설명했다. [R2-01]

**I** 거리, 화면 크기, 시야 중심, 조작 자세가 서로 얽힌다. '콘솔은 구석, PC는 중앙'이라는 규칙으로 축약하면 PC에 패드를 연결해 멀리 앉는 사람을 놓친다. HUD를 배치할 때는 전투 중심, 적의 전조, 체력/자원/쿨다운을 번갈아 읽는 경로를 장면 단위로 평가해야 한다. 검은 패널의 면적이나 중앙 빈 공간 비율만으로 판단하지 않는다.

#### 3. 스킬·입력장치: 구조의 공통성과 동작의 차이

**V** 2020년 공식 550×309 GIF의 한 프레임에는 Mouse / Controller로 나뉜 같은 계열의 스킬 그리드가 있다. 패드 쪽에는 버튼 대응 표식과 하단 Close 안내가 보인다. 저해상도이므로 세부 텍스트·클릭 목표의 실물 크기는 판독/측정하지 않았다. [R2-V1]

**D** 2023년 접근성 안내는 키보드·마우스와 컨트롤러의 입력 재지정, 스킬 누르고 있기 대신 토글, 텍스트 크기 3단계, 커서 크기 조절을 설명한다. [R2-02]

**I** 같은 좌표계를 유지해 입력 전환 때 화면을 다시 학습할 필요를 줄이되, 포인터 드래그를 패드에서도 그대로 흉내 내게 할 필요는 없다. 복잡한 스킬 선택은 '목록 탐색 → 상세 확인 → 배치/변경 → 적용 → 전투 복귀'로 나누고, 전투 중 실행과 메뉴 편집 모드를 확실히 구별해야 한다. 토글을 제공했다면 켜짐/꺼짐 상태, 행동 불가 시 이유, 메뉴 닫기 뒤 유지 여부도 명세 대상이다.

**U** 최신 키보드↔패드 전환 시 포커스·툴팁 보존, 스킬 초기화 비용 표시, 적용 전 취소, 서로 의존하는 노드 제거 오류, 지도/상점까지의 전체 메뉴 깊이는 이 자료로 확정하지 않는다.

#### 4. 색은 미학이자 상태 언어이며, 단독 채널이면 부족하다

**D** 출시 전 공식 안내에는 희귀도별 전리품 소리와 땅에 떨어진 아이템의 주변 소리, 선택 색상의 윤곽 강조, 내장 및 외부 스크린리더 지원이 있다. 메뉴 읽기 속도·음량·목소리도 조절할 수 있다. [R2-02]

**I** 어두운 세계관을 위해 장식의 채도를 줄이는 것과 위협/선택의 대비를 줄이는 것은 다른 결정이다. 희귀도는 색+모양+소리처럼 여러 채널로 제공하고, 긴급 정보는 배경 변화·파티 이펙트 속에서도 구별돼야 한다. 소리 추가만으로 접근성이 해결되는 것도 아니다. 전투 소음과 겹침, 헤드폰 부재, 청각·시각 지원 동시 사용, 스크린리더의 과도한 낭독 큐를 확인해야 한다.

#### 5. 퀘스트·지도·탐험 복귀: 같은 목적지를 여러 감각으로 전달

**D** Vessel of Hatred 관련 공식 글은 Journal에서 선택한 퀘스트/작업의 목적지를 자동 핀으로 지정하고, 미니맵 경로·공간 음향 핑·캐릭터 주변 방향 나침반으로 이어지는 흐름을 설명한다. 오디오의 음량/간격과 나침반 색을 바꿀 수 있다. [R2-03]

**I** 지도에서 얻은 경로를 머릿속에 유지한 채 이동해야 하는 부담을 줄이는 흐름이다. Journal→목적지→경로의 데이터가 일치해야 하므로, 지도와 퀘스트가 별개 서비스처럼 업데이트되면 UX는 깨진다. 정적 화살표를 예쁘게 그리는 것보다 목적지 갱신·실제 통과 가능 경로·종료 조건의 정확성이 우선이다. 나침반은 넓은 지형 방향을 알려도 문·높낮이·우회 경로의 문제를 모두 해결하지 못한다. 이 한계는 기능의 논리적 범위에 대한 해석이다.

#### 6. 오류 사례를 패치노트에서 회수하기

**D** 3.0 계열 공식 패치노트는 컨트롤러로 전리품 필터를 편집하지 못하는 문제, 지도 요소 중첩, 실제와 맞지 않는 일부 툴팁, 초기 진입의 스크린리더 오안내 등을 수정했다고 기록한다. [R2-04]

**I** 잘된 화면뿐 아니라 **상태가 어긋난 이력**을 테스트 목록으로 변환할 수 있다. 예: 패드로 모든 필터 연산에 도달 가능한가, 여러 지도 조건이 동시에 켜지면 라벨이 겹치는가, 수치 재계산 뒤 툴팁도 갱신되는가, 시각 텍스트와 음성 값이 같은가. '수정했다고 공지'는 해당 버그의 현재 전 기기 해결을 우리가 재현했다는 뜻이 아니다.

#### 이 사례의 결론과 적용 금지선

Diablo IV에서 가져올 원리는 '고딕 스킨'이 아니라 반복 관리의 목적, 실제 전투 시야, 서로 다른 입력 경로, 다감각 상태 전달의 정합성이다. 공식 개발자의 목표는 효과가 입증된 결과와 분리한다. 접근성 옵션 개수만 세어 총체적 접근성을 평가하지 않는다. 핵심 상점·장비 비교·복귀 상태를 빠짐없이 분석하려면 한 출시 빌드의 공개 플레이 시연을 추가 수집해야 하며, 본 문서는 이 부분을 완료로 표시하지 않는다.

## 카드게임편

### 사례 C1. Hearthstone: 보드의 즉시 판단과 컬렉션의 정밀 탐색을 나누기

#### 증거 범위

2015년 공식 모바일 출시 이미지, 2018년 Collection Manager 공식 이미지·설명, 2016년 필터 설명, 2018년 시작 손패 안내, 2026년 복귀자 안내를 읽었다. 서로 다른 시기의 기능 자료를 구별하며 하나의 현재 클라이언트처럼 합치지 않는다. 2015년 화면은 모바일 대응의 역사 사례이지 최신 UI 규격표가 아니다.

#### 1. 보드의 계층: 세부 본문보다 당장 판단할 숫자

**V** 모바일 출시 원본(950×534)은 위에 상대, 아래에 자신, 가운데 두 진영의 하수인, 오른쪽 End Turn, 왼쪽 세로 행동 기록 아이콘을 배치한다. 손패는 오른쪽 아래에서 부분적으로 겹친다. 하수인 공격/생명 숫자는 크게 남고 긴 카드 본문은 보드에서 사라진다. 초록 테두리는 일부 손패/영웅 능력 주위, Z는 일부 하수인 위에 보인다. 이 화면 관찰만으로 모든 초록 테두리의 정확한 상태 규칙을 확정하지 않는다. [C1-V1]

**I** 컬렉션 카드와 전장 하수인이 서로 다른 정보 표현인 이유를 읽어야 한다. 선택 전에는 규칙 본문이 중요하지만, 배치 후에는 현재 수치와 행동 가능 여부가 중요해진다. 하나의 큰 카드를 끝까지 그대로 쓰는 대신 상태에 맞춘 표현을 두되 카드의 정체성은 유지한다. 초보에게 규칙이 사라진 것처럼 느껴지지 않도록 다시 읽기 경로가 필요하다.

**색·면적의 정성 분석** 밝은 중성 보드가 하수인 실루엣과 숫자의 읽기 바탕이 되고, 주변 장식이 프레임을 형성한다. 생명은 붉은 방울, 공격은 다른 모양의 표식으로 묶여 숫자의 역할을 공간/모양으로도 구별한다. 실제 대비율·색 면적·터치 목표 크기는 측정하지 않았다. 장식적인 테이블 모티프를 고밀도 보드에 무조건 이식하면 정보가 늘 때 사용할 공간을 잃을 수 있다.

#### 2. 카드 읽기 → 대상 선택 → 확정은 각각 별개 상태

**I·설계 분석** 이 보드에서 필요한 흐름은 손패 훑기 → 카드 세부 읽기 → 비용과 보드 조건 확인 → 플레이/대상 지정 → 해결 결과 확인 → 다음 행동 또는 턴 종료다. '카드를 움직였다'는 시각 효과만으로는 읽기인지, 드래그 시작인지, 확정인지 구분하기 어렵다. 터치에서 손가락 아래에 최종 목표가 가려지는지를 검증해야 한다.

**U** 이 조사에서는 실제 게임에서 카드 확대, 손가락 떼기의 확정 경계, 대상 선택 중 취소 입력, 불가능한 대상 표시, 비용 부족 오류의 문구, 일반 행동의 실행취소 가능 여부를 재현하지 않았다. 따라서 'Hearthstone은 이렇게 취소된다'는 구체 입력 규칙을 창작하지 않는다. SNAP처럼 턴 일괄 되돌리기가 있다고 가정해서도 안 된다.

**권장 검증 장면** 자기 하수인/적 하수인이 모두 목표가 되는 주문, 여러 동일 아트 하수인, 손패가 많은 상태, 경계에 놓인 턴 종료 버튼, 남은 비용은 충분하지만 다른 조건이 부족한 카드. 이 장면에서 강조 표시의 규칙과 실제 실행 가능 여부가 일치하는지 체크한다.

#### 3. 시작 손패: 덱을 이해하는 또 하나의 문턱

**D** 공식 Mulligan 안내는 선공/후공의 다른 시작 손패와, 시작 전 원하는 카드를 다시 섞어 교체할 기회를 설명한다. [C1-02]

**I** 카드게임 온보딩은 메뉴 사용법만 가르쳐서는 부족하다. 시작 선택 자체가 덱의 목적·상대·비용 곡선에 의존한다. 튜토리얼에서는 무엇을 유지/교체하는지 선택 상태를 분명히 보여주고, 확정 직전에 결과가 아닌 변경 대상만 명확히 표시해야 한다. 도중 확정 취소와 타이머 규칙은 별도 확인 항목이다. 전략적 추천을 하더라도 선택 이유와 직접 수정 가능성을 유지한다.

#### 4. 컬렉션과 덱: 목적에 따른 상세 탐색

**V** 2018년 1270×780 공식 컬렉션 이미지에는 상단 직업 탭, 중앙 4열×2행 카드, 오른쪽 My Decks 목록, 하단 비용 필터/검색/Crafting, 우하단 Back이 있다. 검색창에는 Attack:6이 보이며 검색창 오른쪽 X가 보인다. 페이지 번호와 보유 장수도 카드 그룹 근처에 보인다. 이 열·행 수는 **해당 이미지**의 측정 가능한 관찰이며 모든 해상도/버전의 규칙이 아니다. [C1-V2]

**D** 공식 문서는 공격/생명/마나/보유 수, 희귀도, 카드 종류, 신규/미보유 등의 검색을 설명한다. 2016년 안내에는 비용 필터와 검색어가 충돌하면 결과가 없을 수 있다는 경고도 있다. [C1-03][C1-04]

**I** 훑어보기의 카드 그림·비용 필터와 정밀 검색의 문법을 함께 제공한다. 장점은 숙련자의 반복 조회를 짧게 만들 수 있다는 것. 부담은 문법 학습과 숨은 필터의 교집합이다. 자신의 덱빌더에서는 활성 필터를 칩으로 드러내고, 0건일 때 '카드 없음'과 '조건 충돌'을 구별하며 전체 해제 경로를 제공하자. 이것이 Hearthstone에 이미 모두 구현됐다는 뜻은 아니다.

**깊이 모델** 2026년 공식 복귀자 안내의 추천 덱 진입은 메인 메뉴 → My Collection → New Deck → 직업 선택 → 추천 덱 선택이다. 덱 코드를 복사해 Collection을 열면 덱을 가져오며 없는 카드는 회청색으로 나타난다고 설명한다. [C1-05] 의미 선택 4단계의 경로지만 클릭 수·모달 개수·현재 플랫폼 차이는 미실측이다.

**I** 자동 완성/덱 가져오기는 결정을 지워 버리는 것보다 시작 가능한 초안을 제공하는 데 가치가 있다. 미보유 카드를 단순히 흐리게 하는 데 그치지 않고 누락 개수, 대체 후보, 플레이 가능 여부를 설명해야 한다. 현재 도구가 이를 모두 제공한다고 주장하지 않는다.

#### 5. 모바일을 단순 축소판으로 보지 않기

**D** 2014년 공식 개발 글은 작은 화면에 맞춘 인터페이스 재설계 때문에 폰 대응에 추가 시간이 필요했다고 설명했다. [C1-06]

**I** 2015년 모바일 이미지의 손패 밀집은 일러스트·규칙·보드·터치 면적 사이의 협상이다. 화면상의 카드 너비만 보고 누를 수 있는 면적을 계산하면 겹침·팬 펼침·선택 확대를 놓친다. 모바일 카드 UI는 '평상시 카드 가장자리 노출', '읽기 확대', '드래그', '대상 선택'을 별도 스크린으로 수집해야 한다. 가로 화면에서 양손 파지, 오른손/왼손 조작, 기기 노치·홈 제스처, 중단 후 복귀를 따로 시험한다.

#### 6. 오류·복귀·수익화 평가

**D** 2026년 복귀자 글은 추천 덱, 체험 카드, 보상, 팩과 상점의 경로를 함께 안내한다. [C1-05]

**I** 다시 플레이하기를 돕는 경로와 보상 수령·결제 유도는 평가를 분리해야 한다. 복귀자가 다음 한 판까지 얼마나 명확히 도달하는가와 매출 전환은 같은 UX 지표가 아니다. 체험 기간 종료, 미보유 카드, 실제 결제와 게임 재화 비용을 섞어 표시하면 충분한 이해 없이 행동하게 만들 수 있다. 그 위험을 따져야 하며, 단일 홍보 페이지로 실제 결제 화면이 다크패턴이라고 단정하지 않는다.

**U** 덱 편집 중 Back의 저장/취소 의미, 미완성 덱의 큐 진입 오류, 카드 제작/분해 확인, 네트워크 중단 때 턴/패 정보 복구, 화면 읽기 접근성, 최신 폰의 정확한 카드 확대 동작은 후속 검증 대상이다.

### 사례 C2. MARVEL SNAP: '배치 → 제출 → 동시 공개'의 상태 경계를 드러내기

#### 증거 범위

공식 도움말, 2024년 3·4월 패치, Game Overview의 공개 12.17초 카드 시연, 2026년 8월 표기의 공식 Quick Guide 도해를 읽거나 관찰했다. 도해 상단은 55.8.35+7을 당시 버전으로 적지만 이를 조사일의 최신 버전이라고 쓰지 않는다. App Store는 57.17.0을 표기하고 도움말 목록은 또 다른 버전을 적는다. 이 보고서는 최신 버전 판정을 목적으로 하지 않으며 버전별 자료를 혼합하지 않는다. **게임 실행은 하지 않았다.**

#### 1. 보드·핸드·카드의 정보 구조

**D/V** 2026년 8월 도해는 일반적인 경기의 12장 덱, 6턴 기본 구조, 세 구역과 구역당 배치, 두 구역 승리를 설명한다. 카드/구역 효과와 다른 모드는 기본 규칙을 바꿀 수 있다. 도해의 카드 정보는 좌상단 비용, 우상단 파워, 능력 텍스트의 역할을 나눈다. 보드 설명 화면에는 세 구역의 상대/자신 점수와 위아래 카드군이 보인다. [C2-01][C2-02]

**V** 공식 PC형 가로 시연의 0.771초 일시정지 프레임에는 중앙 세 구역, 아래 핸드, 좌하단 Retreat, 우하단 End Turn, 왼쪽 에너지 구체, 오른쪽 큐브가 보인다. 10.974초에는 큰 Spider-Man 카드와 이동 선이 보드 위를 덮으며 하단 오른쪽은 Playing 상태다. 1920×1080 원본을 브라우저 축소 뷰로 관찰했고 게임 빌드 번호는 없다. [C2-V1]

**I** 전장 전체 합계만이 아니라 구역별 소계가 의사결정 단위다. 정보를 카드 하나에 몰아넣기보다 구역 규칙·현재 점수·남은 배치 가능성을 함께 읽게 해야 한다. 세로 모바일의 에너지 하단 배치 설명을 PC 시연의 좌측 배치에 그대로 적용하면 문서가 틀린다. 레이아웃 이름에 플랫폼·화면 방향을 반드시 포함해야 한다.

**정보 밀도 원칙** 핸드는 아직 선택하지 않은 카드의 후보군, 보드는 확정/임시 결과, 크게 확대한 카드는 규칙 읽기 또는 해결 중 연출이다. 같은 확대 표현이라도 사용자 제어 확대와 자동 연출을 구별해야 한다. 큰 연출이 본문·구역 점수를 가리는 시간은 정지 화면의 여백만으로 알 수 없으므로 동영상 시간 측정 과제로 남긴다.

#### 2. 턴을 한 버튼으로 취급하지 않는 상태 모델

아래는 공식 설명에서 재구성한 **분석 모델**이며 직접 플레이 추적 로그가 아니다.

1. 읽기: 손패·에너지·구역 효과·공개 우선순위를 확인
2. 임시 배치: 카드를 구역에 놓고 이동·기타 행동을 계획
3. 수정: 임시 행동을 역순으로 되돌리거나 Undo All Actions 사용
4. End Turn 제출: 자신의 준비 완료 상태. 상대의 준비 상태에 따라 경계가 달라짐
5. 양쪽 준비 완료 후 공개/해결: 순서대로 효과·수치 변화가 발생
6. 다음 턴 또는 결과: 새로운 정보에 따라 다시 판단

**D** 도움말은 배치한 카드를 역순으로 손으로 되돌리거나 에너지 구체에서 Undo All Actions를 호출할 수 있다고 설명한다. 2024-03-12 패치는 상대가 턴을 끝내지 않았을 때 제출을 취소하고 배치 단계로 돌아갈 수 있게 했다고 명시한다. [C2-03][C2-04]

**I** 되돌리기는 하나의 기능이 아니다. '카드 한 장 배치 취소', '이번 턴의 모든 준비 취소', '준비 완료 제출 취소', '이미 드러난 결과 되돌리기'는 권한과 정보 조건이 다르다. 자신의 게임에서는 각 단계에 가능한 행동을 표로 명세해야 한다. 공개된 상대 정보까지 보고 과거를 되돌릴 수 있게 하면 공정성 자체를 바꾸므로 UX 편의만으로 판단해서는 안 된다.

**발견성 비판** 에너지 구체는 비용/잔량처럼 보이는데 그 안에 전체 취소가 있다. 이는 화면을 덜 붐비게 하지만 의미상 숨은 명령이 될 수 있다. 새 제품에는 명시적 취소 버튼, 첫 사용 힌트, 선택 행동 목록 같은 대안도 비교하자. '기능이 있으니 발견하기 쉽다'고 결론 내리지 않는다.

#### 3. 공식 자료가 서로 다를 때 어떻게 처리할 것인가

**D** 조사일에 열린 개별 공식 FAQ는 여전히 End Turn 뒤에는 행동을 되돌릴 수 없다고 적었다. 그러나 위의 2024-03-12 패치는 조건부 Undo End Turn을 도입했고, 2024-04-10 패치는 상대 Snap 직후 취소 불가와 End Turn 실패/효과 표시 문제를 수정했다고 기록한다. [C2-04][C2-05][C2-06]

**판정** FAQ의 절대적 '불가'를 현재 규칙으로 채택하지 않는다. 날짜와 변경 내용을 가진 패치를 근거로 **2024년 도입된 조건부 동작**을 설명한다. 최신 모든 모드의 현재 동작, 네트워크 지연 직전/직후의 취소 경계는 플레이/최신 시연 확인 전까지 U다. 문서의 수집일이 오늘이라는 사실은 그 내용이 오늘의 규칙이라는 보증이 아니다.

**I** 실제 설계에서는 클라이언트의 End Turn 라벨과 서버가 수락한 상태가 어긋나면 '다시 누르면 제출인지 취소인지'부터 모호해진다. 중복 탭, 상대 동시 제출, 저속 네트워크, 타임아웃, 앱 중단을 각각 상태 전이로 다뤄야 한다. 단순 버튼의 눌림 효과를 고치는 것만으로는 해결되지 않는다.

#### 4. 상대 행동·우선순위·기록: 예측 가능한 불확실성

**D/V** 2026년 8월 Quick Guide는 공개 우선순위를 현재 구역 우세, 동률이면 점수 차, 그마저 같으면 무작위로 설명하고 이름 테두리 발광을 신호로 제시한다. 옛 개별 FAQ의 짧은 '동률이면 무작위'만 복사하면 중간 기준을 누락한다. [C2-01][C2-07]

**D** 2024년 3월 패치는 플레이어 아바타 → Destroyed/Discarded에서 자신/상대의 해당 카드 정보를 볼 수 있게 했다고 설명한다. 되돌아오는 일부 파괴 카드는 그 목록에 남지 않는다는 예외도 있다. [C2-04]

**I** 숨겨야 할 상대 손패/의도를 드러내지 않으면서 이미 공개된 정보를 다시 볼 수 있게 하는 것은 기억력 부담을 줄인다. 다만 묘지 목록은 사건의 시간순 전체 로그와 동일하지 않다. '현재 파괴된 카드 집합'과 '아까 무엇이 왜 일어났는지'를 구분하자. 우선순위가 이름의 빛만으로 표현되면 작은 화면·저시력·화려한 배경에서 놓칠 수 있으므로 텍스트/아이콘/읽기 지원을 함께 검토해야 한다.

#### 5. 색·카드 읽기·긴 규칙

**D** 개별 도움말은 버프/불리한 변화에 따라 수치가 녹색/붉은색으로 나타난다고 설명한다. [C2-08]

**I** 비용 감소와 파워 증가를 모두 '유리함'으로 묶는 시각 언어는 계산을 단축할 수 있지만, 낮은 파워가 유리한 구역처럼 게임 맥락이 바뀌면 '녹색 = 지금 최선'은 성립하지 않는다. 표시는 수치의 변경 상태이고 전략적 추천은 아니다. 기본 수치, 현재 수치, 변화 원인/지속 기간을 상세 읽기에서 찾을 수 있어야 한다.

**U** 모바일 길게 누르기/탭의 최신 확대 동작, 규칙 본문 최대 길이, 한국어의 줄바꿈·최소 글자 크기, 스크린리더의 구역/카드 읽기 순서, 색각 보조 기능은 이 조사에서 확인하지 않았다. App Store에 접근성 기능이 신고되지 않았다는 문구를 기능 부재의 증거로 쓰지 않는다.

#### 6. 덱 편집·정렬·자동 구성과 복귀

**D** 공식 도움말은 Collection에서 Sort와 Filter를 나누며 이름·비용·파워·최근 획득 등의 정렬, 카드 종류·비용·미보유 등의 필터를 설명한다. Smart Deck은 0장 이상을 선택해 나머지를 자동 구성하는 기능으로 설명된다. [C2-09][C2-10]

**I** 카드 읽기/필터/추천을 오가더라도 사용자의 초안과 선택 카드는 유지해야 한다. 자동 덱은 '무엇을 고정했고 무엇을 채웠는지', 실제 보유 상태, 되돌리기를 보여줘야 신뢰할 수 있다. '괜찮은 덱을 만든다'는 공식 표현은 승률 검증 자료가 아니다. 추천 덱 생성과 큐 입장을 하나로 합쳐 사용자가 결과를 검토할 기회를 빼앗지 않는다.

**D·오류 이력** 3월 패치는 일부 화면 전환의 정렬 초기화와 배경 클릭 통과 등을 문제로 기록했고, 4월에는 정렬 초기화·배경 잘못 선택·관련 튜토리얼 멈춤 문제의 수정을 적었다. [C2-04][C2-05]

**I** 이것은 모달이 '시각적으로만 위에 떠 있는지', 포커스/입력까지 막는지를 검사할 이유다. 그리드를 열기 전 검색·정렬·스크롤·선택 덱을 복귀 계약으로 정의한다. 현재 동일 버그가 남아 있다고 주장하지 않는다.

#### 7. 시간·실수·모바일 환경

**D** 시간 안내 FAQ는 End Turn 버튼의 시간 막대, 임박 시 붉은 화면 신호, 시간 만료 시 현재 준비 행동 자동 실행을 설명한다. 오래된 자료이므로 정확한 초 단위 길이와 모든 모드의 동일 적용을 주장하지 않는다. [C2-11]

**I** 종료 버튼이 커 보이는지만 보지 말고, 시간 압박 아래서 낭독/확대/대상 선택을 마칠 수 있는지 보자. 손가락이 카드와 목적지를 가리는 문제, OS 알림 후 복귀, 세로 한손 조작, 화면 회전·접힘형 화면 변화, 동시에 상대가 끝내는 경합을 별도 시험한다. 실수 방지를 위해 매 카드마다 확인 팝업을 넣으면 짧은 턴을 더 압박할 수 있다. 임시 배치의 선명함과 조건부 취소가 확인창보다 적합한지 비교할 필요가 있다.

#### 8. 수익화·위험 노출은 별도 평가

**D·역사 자료** 2024년 3월 공지는 구매 직후 금 지급과 이후 30일간 일별 금을 받는 Gold Pass도 함께 소개했다. [C2-04]

## 두 편을 나누는 이유: 공통 디자인 시스템, 다른 상태 계약

### RPG에서 먼저 풀 문제

- 세계는 계속 움직인다. HUD를 읽는 동안 전투 장면을 놓칠 수 있으므로 중앙 시야·주변 감시·반복 참조가 중요하다
- 같은 캐릭터가 탐험·전투·장비 정리·스킬 선택·대화·상점을 오간다. 닫기 뒤 원래 목표와 입력 상태를 잃지 않는 것이 핵심이다
- 정보는 긴 시간에 누적된다. 소지품, 퀘스트, 스킬·성장 단계의 깊이를 분류와 지름길로 관리해야 한다
- 모델의 중요한 단위는 '현재 세계 맥락 + 선택 대상 + 열려 있는 관리 화면'이다. 메뉴가 게임을 일시정지시키는지는 게임/모드마다 반드시 확인한다

### 카드게임에서 먼저 풀 문제

- 선택은 규칙과 자원을 소비한다. 카드 읽기·적합성·대상·제출·해결의 경계가 핵심이다
- 숨겨진 정보는 의도된 재미일 수 있다. 공개 정보 접근성 개선과 비공개 정보 노출을 혼동하지 않는다
- 임시 배치와 서버 확정 사이의 상태가 결과를 바꾼다. 실행취소는 시간/정보/상대 행동 조건과 함께 설계한다
- 모델의 중요한 단위는 '턴/단계 + 카드·구역 상태 + 공개 우선순위 + 남은 자원 + 제출 상태'다. 장식적인 카드 크기보다 이 상태를 설명할 수 있는지가 중요하다

### 공통으로 재사용할 원리

1. **같은 객체, 여러 보기**: 장비 목록/비교/상점, 카드 컬렉션/핸드/보드에서 동일한 객체 식별과 현재 상태를 유지
2. **정보 계층**: 항상 필요한 값, 상황별 값, 요청 시 펼치는 상세를 구분. 상세를 숨겼다면 발견 가능한 열기 경로도 제공
3. **맥락 보존**: 정렬·필터·스크롤·초점·대상·초안이 열기/닫기/뒤로/장치 전환 후 어떻게 남는지 명시
4. **일치하는 피드백**: 텍스트·수치·테두리·애니메이션·소리·스크린리더가 같은 상태를 전달
5. **이유와 회복**: 불가능한 행동에는 이유와 다음 행동을 연결. 과도한 확인창 대신 위험에 맞는 임시 상태/되돌리기/확정 적용
6. **입력별 동등한 결과**: 공통 배치를 유지해도 터치·마우스·패드의 동작은 달라도 됨. 전환 후 위치 기억과 초점 이동을 검사
7. **성공과 좋은 UX를 분리**: 인기·매출·플레이 시간·복귀율은 각각 다른 지표. 혼란·강요·시간 압박으로 만들어진 행동을 좋은 경험으로 평가하지 않음

## 다음 편을 쓸 때 사용할 수집 시트

각 화면마다 아래 기록을 하나씩 만든다. 하나라도 관찰하지 못했으면 빈칸을 추정으로 채우지 않는다.

- 게임/장르/모드/자료 날짜/공식 빌드/플랫폼/입력장치/언어
- 작업 이름과 출발 상태: 예 '상점의 방어구를 장착 중인 장비와 비교'
- 목표 정보: 현재 장비, 후보, 차이, 가격, 소지금, 장착 조건
- 진입 경로: 노출된 메뉴 경로와 상황 지름길 각각
- 화면 범위: 전체 화면/일부 창/비교 패널/툴팁/모달
- 구조: 정보 그룹·열/행·정렬·누락·텍스트 길이·겹침
- 크기: 원본 해상도, UI 스케일, 표시 해상도, 인게임 컨트롤인지 웹 편집 이미지인지
- 상태: 기본/포커스/선택/불가/실행 중/성공/오류/취소/복귀
- 행동: 입력 시작·중간·확정·취소의 경계, 장치별 경로
- 색·형태·소리: 각각 무엇을 의미하는지, 중복 채널이 있는지
- 실패와 회복: 전제조건·연결 장애·타임아웃·장치 변경·언어 변경·중복 입력
- 복귀 계약: 선택·스크롤·필터·초점·초안·세계/턴 상태의 보존 여부
- 실증 자료: 관찰 프레임/타임스탬프/원본 URL, 직접 실행 여부, 보지 못한 것
- 평가: 좋아 보이는 이유의 가설, 반증될 조건, 따르지 말아야 할 조건, 테스트 과제

## 측정 방법과 출판 안전선

- 원본 이미지의 naturalWidth/naturalHeight 또는 원본 파일 크기를 기록하고, 창/버튼 경계가 실제로 보일 때만 좌표를 잰다. 비교 시 동일 UI 스케일·언어·장면을 고정한다
- 이미지에서 얻은 픽셀은 게임 논리 좌표나 모바일 dp/pt와 다르다. 원본을 모르면 상대적인 '전체 화면 대비 영역'만 보조 관찰로 사용한다
- 색 비율을 나중에 잴 때는 월드/카드 아트/장식/HUD를 마스킹하고 샘플링 규칙을 공개한다. 단일 스크린샷의 픽셀 비율을 게임 전체 디자인 토큰으로 일반화하지 않는다
- 시간이 포함된 UI는 애니메이션 전·중·후를 수집한다. 정지 장면은 정보의 위치를 보여주지만 선택 반응 속도·혼란·인지 부하를 입증하지 못한다
- 장애 사용자 접근성은 옵션의 존재와 실제 과업 완료를 별도로 평가한다. 스크린리더 지원 목록만으로 모든 과업을 가능하다고 쓰지 않는다
- 공식 화면은 분석·비평 목적의 출처로 연결한다. 게임 아트/스크린샷을 자신의 새 제품 자산으로 복제할 수 있는 라이선스로 해석하지 않는다
- 다음 버전 매뉴얼에는 고정된 자료 날짜와 변경 이력을 둔다. 같은 기능의 공지·도움말·영상이 다르면 가장 구체적인 빌드/날짜를 우선하고 충돌을 표시한다
